# 부과 V2 구현·적용·복구

2026-09-07 12:00 KST. **운영 웹 배포·자료 이관·활성화 완료(`enabled=true`, `paused=false`).** 회비 관리의 기존 주소에서 새 기능을 사용한다. 첫 DB 설치는 11:24 KST였고 당시 비활성이었으며, 이후 TODO 사용 흐름 보완과 운영 전환까지 완료했다.
[기획](ACCOUNTING_PLAN.md)과 [기존 자료 조사](ACCOUNTING_IMPLEMENTATION_REVIEW.md)를 바탕으로 구현했다. 이 문서는 실제 구현의 범위와 전환 방법을 설명한다.

## 1. 적용한 동작

- **부과 취소 후 발행:** 선택한 유효 부과만 취소한다. 원금·대상·원부과 연결을 가진 새 부과를 만들고, 원부과에 썼던 납부금을 재사용한다. 부족분은 미납, 남는 돈은 원래 납부자의 회원 잔액이다. 같은 입금의 클럽 직접 수입과 다른 부과 납부는 유지한다. 취소와 새 발행은 한 트랜잭션이다.
- **미납·입금 이월:** 회원·대상 월을 고르고 미납과 입금 잔액의 전액/일부를 한 번에 넘긴다. 부과와 통장 거래는 추가하지 않는다. 미납은 납기별로 나뉘고, 돈은 지정 월부터 사용할 잔액이 된다. 여러 달로 나눈 납기도 재발행 화면에 유지하며, 금액 변경 시 납기별 합계를 다시 맞춘다.
- **이월금 사용:** 해당 월부터 본인의 납기가 도래한 실제 부과에 자동 적용한다. 납기→발행 순, 원입금 날짜 순이다. 발행·이월 작업 및 5분 간격 예약 작업에서 반영한다. 조회는 납부를 만들지 않는다. 남는 돈은 다음 부과까지 보관한다. 다른 사람 대납은 운영진이 대상을 선택하고 확인해야 한다.
- **환불:** 출금 월과 관계없이 전체 원입금을 검색한다. 한 출금은 한 원입금에 연결하고 같은 입금을 여러 차례 부분 환불할 수 있다. 환불 대기금은 납부에 쓰지 않는다. 환불 연결 해제 시에도 돌려줄 돈을 예약해 재사용을 방지한다. 실제 송금/출금 삭제 기능은 없다.
- **공통 집계:** 회원의 현재 낼 돈·향후 미납·이월 입금·환불 대기·사용 이력, 운영진의 회원/묶음/통장 집계가 새 원장을 사용한다. 운영진과 회원의 월 장부는 같은 RPC를 사용한다. 월 마감 잠금은 없고 과거 분류는 재집계할 수 있다.
- **구분과 검증:** 같은 이름의 회원은 각 ID로 선택하며 출생연도·성별·보조 식별자를 표시한다. 대관 후보는 KST 날짜·장소가 겹칠 때 시각을 추가하고, 시간도 겹치면 회차명·번호로 구분한다. 확정 전 원부과/원입금·대상·금액과 변경 결과를 확인한다. 계산 규칙 후보의 금액·대상은 확정 시 재검증하며, 수동 지정으로 전환하려면 화면에서 명시한다.
- **기존 경로 보호:** 활성화 중 기존 부과/배분/귀속을 쓰는 API와 직접 쓰기를 차단한다. 회원 비활성·명예 지정으로 과거 미납을 삭제하지 않는다. 이미 발행한 회차의 총액 수정은 취소 후 발행을 안내한다. 향후 자격·단가·미발행 회차 설정은 기존 설정을 사용한다.

설치 직후에는 `dues_v2_control.enabled=false`다. 기존 화면·원장을 계속 사용하며, 운영진이 전환할 때 전체 현재 자료를 이관한다. 현재 자격·단가로 7·8월 부과를 재계산하지 않는다. 기존 회원 잔액도 자동 이월 동의로 바꾸지 않는다.

원입금 보존식과 부과 잔액 보존식을 명령마다 검사한다. 모든 금융 변경은 공통 제어 행 잠금, 예상 revision, 요청 UUID로 직렬화한다. 미리보기는 실제 명령을 하위 트랜잭션에서 실행한 후 되돌린다. 확정 재시도는 같은 요청 UUID를 사용해 중복 납부를 방지한다.

원부과·은행 거래 ID는 유지한다. 새 테이블에는 기존 ID 대응값이 있고, 발행 당시 근거와 취소/후속 부과 관계가 남는다. 일반 작업은 변경된 행의 전후 상태, 전환/복귀 작업은 전체 상태를 기록한다. 이는 월 장부 고정 기능이 아니라 처리 복구용 기록이다.

## 3. 적용 순서

아래는 전환 절차다. 2026-09-07 11:24 KST 기준으로 DB 설치와 예약 작업 등록까지 완료했고, 새 클라이언트 배포 및 실제 활성화는 별도 단계다.

1. 현재 운영 릴리스와 DB 백업을 확보한다. `accounting-transition-audit.sql`로 자료의 최신 건수·금액과 이관 불가 조건을 확인한다. 미납의 업무상 면제 여부는 이관과 분리한다.
2. `accounting-v2-snapshot.sql`의 읽기 전용 결과를 **저장소 밖 JSON 파일**로 추출해 아래 로컬 검증을 실행한다. 파일에는 이름·계좌번호·적요를 넣지 않지만 UUID·거래 금액이 있으므로 Git에 넣지 않는다.
3. 미적용 마이그레이션 목록을 확인한 후 새 SQL과 클라이언트를 배포한다. 새 기능은 비활성 상태로 둔다. 기존 기능의 조회/처리가 정상인지 확인한다.
4. `pg_cron` 확장과 아래 예약 작업이 등록돼 있는지 확인한다. 확장을 제공하는 DB에는 마이그레이션이 작업을 설치한다. 확장이 없는 로컬 DB는 동일 함수를 테스트에서 직접 호출한다. 운영에서 예약 작업이 빠지면 월 변경 자동 발행/이월금 적용을 보장할 수 없으므로 활성화 전에 해결한다.
5. 운영진 **회비 관리 → 부과 운영·복구 → 새 부과 시작**에서 사유를 입력한다. 기존 재무 자료를 포함한 JSON 백업을 다운로드한 후 활성화한다. 그 시점의 전체 부과·납부·입금·환불을 이관한다. 화면 확인 이후 다른 처리가 있으면 revision 충돌로 중단되므로 다시 조회하고 진행한다.
6. 아래 대조 항목을 확인한다. 기존 화면을 열어 둔 탭도 새 모드를 재조회한다. 전환 확인 전의 예전 쓰기는 서버에서 거절된다.

예약 작업 확인(SQL은 조회만 수행):

```sql
select enabled, paused, revision, activated_at
from public.dues_v2_control where id = 1;
select jobname, schedule, command, active
from cron.job where jobname = 'dues-v2-month-and-carry';
```

활성화 직후 대조 기준:

- 기존 부과 건수·원금·납부액·취소/면제·원입금 연결·이월 납기가 일치한다.
- 각 원입금은 `현재 납부 + 실제 환불 + 회원 잔액 + 이월 입금 + 환불 대기 + 클럽 직접 수입 + 미귀속 = 실제 입금액`이다.
- 7·8·9월 각각 항목 수입 합과 실제 월 수입, 항목 지출 합과 실제 월 지출이 일치한다. 항목별 분류는 달라질 수 있다.
- 기존 7·8월 미납 4건/20,000원과 취소 3건/18,000원이 유지된다. 이 값은 2026-09-07 조사 시점 기준이므로 실제 전환 시 변경분은 최신 원장과 비교한다.
- 7·8월 귀속 수입 잔액 1,213,094원은 클럽 수입이다. 이를 회원 이월금으로 만들지 않는다. 8월 미귀속 회원 잔액 2,000원은 동의 없는 자동 사용 대상이 아니다.

## 4. 문제 발생 시 복구

### 잠시 멈추거나 직전 처리만 되돌리기

**부과 운영·복구 → 처리 일시 중지**는 새 확정·자동 적용을 멈춘다. 내역 조회와 실제 은행 거래 수집은 계속된다.

**직전 처리 되돌리기**는 현재 전환 이후의 가장 최근 금융 작업 1건을 전후 기록으로 되돌린다. 취소 후 발행의 원부과·납부 연결도 복원한다. 이후 수집된 실제 입출금은 지우지 않는다. 반복해서 과거 처리로 돌아갈 수 있지만, 중간 작업만 건너뛰어 되돌리는 기능은 아니다. 자동 발행·이월금 적용도 금융 작업에 포함되므로 대상 처리를 이력에서 확인한다.

### 기존 기능으로 전체 복귀

**부과 운영·복구 → 기존 부과로 복귀**에서 영향 건수와 사유를 확인한다. 복귀 직전 백업을 다운로드하고 새 기능을 끈다. 기존 부과·배분 행을 보존했으므로 기존 화면이 그 원장을 다시 사용한다. 새 원장과 처리 이력은 조사용으로 남기며, 삭제하지 않는다.

**새 기능에서 처리한 모든 부과 변경·납부·이월·환불 연결은 기존 기능으로 이어지지 않는다.** 실제 입출금은 남으므로, 전환 이후 거래 및 새 정산 결정은 백업/이력과 대조해 기존 기능에서 다시 처리해야 한다. 이것이 이번 전체 롤백의 범위다. 새 기능에서 한 결정을 유지하며 기존 스키마에 역이관하는 기능은 없다.

웹 화면이 고장 나면 DB 소유자가 `scripts/accounting-v2-rollback.sql`을 사용한다. 동일하게 현재 상태를 보존하고 새 모드를 끈다. 먼저 DB 백업/재무 내보내기를 확보한다. 이 스크립트는 일반 회원용 RPC가 아니다.

코드를 이전 릴리스로 되돌릴 때는 **먼저 서버에서 기존 기능으로 복귀한 뒤** 클라이언트 릴리스를 되돌린다. 새 모드가 켜진 상태에서 옛 JavaScript만 배포하면 옛 쓰기는 보호 장치에 막힌다. 복귀를 위해 새 테이블이나 마이그레이션을 삭제하지 않는다.

계좌에서 실제로 송금한 돈, 회원의 현재 자격, 회비 설정, 미발행 회차의 설정 변경은 회계 복구로 되돌리지 않는다. 실제 은행 재입금은 새 거래로 수집한다. 다시 활성화하면 그때의 기존 원장을 새로 이관하며, 이전에 폐기한 새 원장의 결정을 자동 복원하지 않는다.

### 백업 파일의 범위

화면의 JSON에는 기존 통장 거래·부과·배분·묶음·발행 대기·회비 설정과 새 원장·제어 상태·처리 이력이 들어간다. 운영 자료이므로 접근을 제한해 보관한다. 회원/Auth 전체, 함수 정의, 전체 서비스 데이터까지 포함한 DB 재해 복구 백업은 아니다. JSON 업로드로 전체 DB를 자동 복구하는 기능도 없다.

## 6. 이번 구현의 명시적 범위

- 새 원장이 참조하는 회원·회차·통장 행의 물리 삭제는 외래 키로 제한한다. 이 제한은 새 원장을 보존하는 전체 복귀 후에도 남는다. 기존 `delete_my_account`/`delete_member`로 재무 이력이 있는 회원을 물리 삭제하는 동작도 제한되므로 운영 정책에 포함해야 한다. 비활성 전환은 지원한다. 삭제 기능까지 원래대로 돌리는 스키마 제거는 이 복구 절차에 포함하지 않는다.
- 원입금의 돈 소유자는 한 명으로 유지한다. 대납 대상은 여러 명일 수 있다. 여러 소유자의 자금이 합쳐진 입금은 자동 이관/소유자 분할을 지원하지 않는다. 실제 조사 자료에는 이러한 기존 배분이 없었다.
- 새 회원 진입 알림은 새 원장을 사용한다. 기존 선택 푸시 API는 활성화 중 차단하며(전체 미납 API는 이미 삭제되어 다시 만들지 않음), 새 화면에 일괄 푸시 버튼은 제공하지 않는다. 과거 미납 노출만으로 독촉을 자동 발송하지 않는다.
- 회차 후보는 같은 KST 날짜·장소에 여러 회차가 있을 때만 시간을 표시하고, 시간도 겹치면 회차명·번호로 구분한다. 수동 부과의 참고 회차/회식 명단 선택도 같은 규칙을 사용한다. 이전 부과 명단 복사, 묶음별 업무 완료 체크, 초안 영구 제외 UI는 보조 범위로 남아 있다. 수동 대상은 회원 ID로 선택하며, 초안은 현재 기준으로 다시 확인한다.
- 실제 동명이인 거래의 업무상 오지정 정정이나 기존 미납 면제는 수행하지 않았다. 새 선택 경로에서 동명이인을 합치거나 첫 이름 후보로 자동 확정하지 않는 것을 구현했다.

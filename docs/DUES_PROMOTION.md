# 부과 정식 승격 — 2026-09-11

## 구현 계획

1. 현재 원장·ID·금융 처리 이력을 보존한다. v1 화면과 상태 분기를 제거하고 v2 코드에 기존 `dues` 모듈 경로를 넘긴다. 설정/계좌/메일 수집과 참석 계산은 공통 모듈로 분리한다.
2. 새 마이그레이션에서 기존 금융 테이블을 비공개 `dues_legacy` 스키마에 보관하고 `dues_v2_*` 테이블·함수를 `dues_*`로 승격한다. 함수 본문, 트리거, 예약 작업, 권한도 갱신한다. 이미 적용된 마이그레이션은 수정하지 않는다.
3. 구 화면의 `dues_v2_*` 공개 RPC는 정식 RPC를 호출하는 호환 함수로 유지한다. 이전 v1 금융 API는 차단하고 통장 원본 수정 방지와 요청 중복 방지를 유지한다.
4. 일정 삭제 판단과 실행을 정식 원장에 연결한다. 반복 일정 또는 금융 기록이 연결된 일정은 취소로 보존하며, 기록 없는 일회성 일정만 삭제한다. 실제 실행은 부과 명령과 같은 제어 행 잠금 안에서 다시 판정한다.
5. 마이그레이션 전후 금융 행과 요청 재시도를 대조한다. 정식/호환 RPC, 은행 수집 트리거, 일정 종료 자동 부과, 월 예약 작업, 회원 권한, 삭제 경로를 로컬 PostgreSQL에서 검증하고 기존 브라우저 시나리오·타입 검사·빌드를 실행한다.

## 배포 순서

현재 DB 전체 백업 확보 → 마이그레이션 적용 및 검증 SQL 실행 → 프런트 배포. 현재 원장을 다시 이관하지 않는다. 구 RPC 호환 함수가 있어 기존 열린 v2 화면도 계속 같은 원장을 사용한다. v1 화면으로의 fallback은 제거한다.

`dues_legacy`는 과거 자료 보관용이며 PostgREST 노출 스키마에 추가하지 않는다. 보관 자료의 영구 삭제, 구 RPC 호환 제거, 과거 마이그레이션 squash는 이번 승격 범위에 포함하지 않는다.

운영 백업은 Supabase/PostgreSQL 전체 백업을 사용한다. 기존 `accounting-v2-snapshot.sql`은 최초 v1 이관 시험용이며 현재 운영 원장 백업이 아니다.

## 구현 결과

- 정식 클라이언트: `src/lib/supabase/dues.ts`, `src/store/duesStore.ts`, `src/lib/dues/`.
- 공통 설정·계좌·입금 수집: `duesSettings.ts`. 설정/명예회원 UI는 `components/accounting/`에서 소유하며 현 원장을 갱신한다.
- 이전 관리자/회원/알림 화면 및 금융 API·store는 제거했다. 기존 `/dues`, `/dues/:ym/:page`, `/my-dues` 주소를 유지한다.
- DB 전환: `20260911010000_promote_dues.sql`. 이전 금융 테이블 5개는 `dues_legacy`에 보관하고, 현재 금융 테이블·함수·인덱스·시퀀스·제약 이름을 승격한다. 금융 데이터·제어 상태·이력 17개 테이블의 전후 건수와 행 해시를 트랜잭션 안에서 비교한다.
- 호환 RPC 8개는 현재 명령/조회를 그대로 호출한다. 실행 권한·RLS·epoch·요청 UUID를 유지하고, 익명 사용자나 비관리자에게 쓰기 권한을 추가하지 않는다.
- 일정 종료 자동 부과와 대상 계산 함수를 유지한다. 예약 작업의 실행 명령을 `dues_run_scheduled()`로 갱신하고 기존 작업 이름(`dues-v2-month-and-carry`)·ID·주기·활성 상태·실행 이력은 보존한다. 운영 리허설에서 Supabase가 `cron.job` 직접 수정을 허용하지 않는 것을 확인했다. 공식 `cron.alter_job` API로 명령만 변경한다.
- 삭제 안내와 서버 실행이 같은 원장 판정을 쓴다. 서버는 실행 시 재검증하여 새 선납이 생긴 일정도 취소로 보존한다. 대관 총액 변경 화면의 이전 재발행 안내도 현재 정책에 맞췄다.
- 이전 이관 조사 스크립트는 승격된 DB에서 실행을 거부한다. 현 원장 검증은 `scripts/dues-verify.sql`을 사용한다. 배포 workflow에 단위/DB 테스트를 추가했다.

## 검증 범위

로컬 합성 데이터의 PGlite에서 승격 전후 보존·정식/호환 요청 재시도·권한·은행 수집·실제 일정 종료 트리거·월 작업·일정 삭제를 검증했다. 원장 보존식 실패 시 테이블/함수 이름 변경과 보관 스키마 생성이 모두 롤백되는 것도 확인했다.

운영 배포에서는 PostgreSQL 전체 스키마·데이터 백업을 확보하고 압축 해제 및 SHA-256 검증을 완료했다. 실제 운영 스키마에서 마이그레이션과 관리자 RPC 호환을 실행한 뒤 롤백하여 원상복구까지 확인했다. 이 과정에서 pg_cron 직접 수정 권한 문제를 수정했다. 별도 DB 연결 간 동시 잠금 경쟁은 이번 검증 범위에 포함되지 않는다. 마이그레이션은 잠금 대기가 5초를 넘으면 전체 실패하며 재시도할 수 있다.

2026-09-11 운영 DB에 `20260911010000`을 적용하고 마이그레이션 이력 등록, 원장 보존식, 관리자/회원 조회 및 기존 RPC 호환, 비공개 보관 스키마 권한을 검증했다. 은행 원본 2,296건·현 부과 556건·납부 연결 539건·환불 25건·명령 이력 40건을 포함한 17개 테이블의 전후 행 수와 해시가 일치했다. epoch와 기존 예약 작업(ID 2, 5분 주기, 활성)을 유지했다. 관련 없는 미적용 경기 횟수 마이그레이션은 이번 DB 배포에서 제외했다.

## 1. 이번 설계의 기준

**부과·입금 사용·잔액의 책임을 새로 나누고, 기존 발행과 납부 결과를 그대로 옮기는 방식**을 권장한다. 과거 회비·대관비를 현재 규칙으로 다시 계산하는 작업은 전환에 포함하지 않는다.

사용자 확인에 따라 월 정산은 **해당 월 실제 통장 거래를 현재 분류로 합산하는 화면**으로 둔다. 과거 입금을 다른 부과에 사용하면서 과거 항목별 합계가 바뀌는 것은 허용한다. 월 마감 잠금·확정 장부 스냅샷은 이번 구현의 요구사항이 아니다.

보존할 것은 다음이다.

- 이미 발행한 대상·금액과 취소/면제 결정. 현재 회원 자격이나 참석 명단으로 소급 재생성하지 않는다.
- 실제 입출금의 ID·금액·일시와, 이미 어느 부과에 얼마를 사용하고 얼마를 환불했는지.
- 회원의 현재 미납과 남은 돈. 새 기능 도입만으로 추가 의무나 이월금이 생기지 않는다.
- 과거 입금으로 납부한 이번 달 부과, 이번 달 입금으로 납부한 과거 부과의 연결.

월 장부의 분류 변경 허용과 납부 결과 보존은 양립한다. 예를 들어 8월 입금 30,000원을 회식 24,000원·9월 회비 5,000원·잔액 1,000원으로 사용하면, 8월 장부에 회비 수입 5,000원이 잡힐 수 있다. 9월 회원 회비는 완납이지만 그 사용으로 9월 통장 수입이 생기지는 않는다.

## 2. 실제 데이터에서 확인한 영향

단일 SELECT 집계는 [조사 SQL](../scripts/accounting-transition-audit.sql)로 재실행할 수 있다. 성명·회원 UUID·계좌·은행 적요는 출력하지 않는다. 개별 거래의 업무상 의도까지 판정한 결과는 아니다.

전체 규모는 통장 거래 **2,260건**, 부과 **552건**, 납부 배분 **501건**이다. 운영 DB의 `dues_public_ledger`, `dues_set_session_fee`, `dues_confirm_reconcile`, `dues_link_refund` 함수 본문도 저장소의 해당 최종 마이그레이션과 일치했다. 그 밖의 모든 운영 함수가 일치한다고 검증한 것은 아니다.

| 부과 원월 기준 | 완납 부과 | 완납 금액 | 남아 있는 미납 | 취소 부과 |
| --- | ---: | ---: | ---: | ---: |
| 7월 | 186건 | 1,072,000원 | 2건 / 10,000원 | 2건 / 12,000원 |
| 8월 | 218건 | 1,629,000원 | 2건 / 10,000원 | 1건 / 6,000원 |

따라서 7·8월 **404건 / 2,701,000원의 완납 연결**이 전환 직후에도 그대로 설명되어야 한다. 이 표는 부과 원월 기준이며 월 통장 수입과 같아야 하는 값이 아니다.

### 2.1 이미 달을 넘긴 납부가 있다

| 원입금 → 사용한 부과 | 현재 사용액 | 이관 시 주의 |
| --- | ---: | --- |
| 6월 → 7월 회비 | 5,000원 | 7월 이후 입금만 가져오면 원입금을 잃음 |
| 7월 → 8월 부과 | 44,000원 | 8월 납부를 8월 입금만으로 복원할 수 없음 |
| 7월 → 9월 회비 | 5,000원 | 이미 사용 완료. 새 9월 이월 잔액으로 중복 생성 금지 |
| 8월 → 9월 회비 | 10,000원 | 위와 동일 |
| 9월 → 8월 대관비 | 6,000원 | 8월 말 상태로 되돌려 이관하면 완납이 미납으로 바뀜 |

9월에도 이미 통장 거래 100건과 부과 139건이 있다. **전환 기준은 9월 1일이 아니라 실제 전환 시점의 전체 연결 상태**여야 한다. 6월 부과도 2건 남아 있으므로 과거 의무를 월 필터로 버리지 않는다.

### 2.2 ‘처리가 끝남’과 DB 미납 0은 현재 같지 않다

| 부과 ID | 원내역 | DB 미납 | 처리 원칙 |
| --- | --- | ---: | --- |
| 1062, 1067 | 7월 회비 | 각 5,000원 | 기존 미납으로 이관. 실수 부과인지 확인되지 않았으므로 자동 면제·삭제하지 않음 |
| 1153 | 8월 회비 | 5,000원 | 위와 동일 |
| 4630 | 8월 회차 147 대관비 | 5,000원 | 대상이 현재 운영진. 운영진을 제외하는 현황 계산과 유효 부과 계산이 달라 표시가 바뀔 수 있음 |

새 공통 집계에서 이 20,000원이 더 잘 드러날 수 있다. **새로 부과된 돈과 기존에 남아 있던 돈을 구분해서 검토**해야 한다. 실제 수납 여부·부과 의도는 별도 확인 사항이며, 여기서 누가 잘못 처리했다고 단정하지 않는다. 전환 자체로 미납 독촉을 새로 발송하지 않는다.

취소된 7·8월 부과 ID `1006`, `1008`, `4716`도 취소 상태를 유지한다. 현재 참석자를 기준으로 다시 만들면 이 18,000원이 되살아날 수 있다.

### 2.3 회원에게 남은 돈과 클럽 수입이 섞여 있다

8월 미귀속 입금 잔액은 **2건 / 2,000원**이다. 거래 `14398`, `14857`이 각각 6,000원 입금·5,000원 사용·1,000원 잔액이다. `paid_by`는 없지만 각각 기존 배분의 납부자가 1명이라 소유자 후보를 확보할 수 있다. 기존 ‘돌려받을 돈’ 성격으로 가져오며, 이관만으로 9월 자동 사용에 동의한 것으로 간주하지 않는다.

반면 아래 금액에는 **세션·묶음·레거시 분류에 귀속된 수입**이 들어 있다.

| 입금월 | 귀속 표시가 있는 입금의 `입금 − 배분 − 누적 환불` 잔액 |
| --- | ---: |
| 7월 | 20건 / 673,055원 |
| 8월 | 21건 / 540,039원 |

이 **1,213,094원을 회원 이월금으로 자동 변환하면 안 된다.** 귀속 의도를 유지해 클럽 수입으로 옮기고, 의미가 충돌하는 건은 확인 대상으로 남긴다. ‘아직 부과에 쓰지 않음’은 ‘회원에게 돌려줄 돈’의 충분조건이 아니다.

추가로 확인한 경우:

- 7월 23건·8월 19건은 `batch_id`와 `category_id`가 함께 있다. 같은 돈의 이중 소유로 가져오지 말고 기존 의미를 확인해 한 귀속으로 옮긴다. 두 필드가 있다는 사실만으로 원데이터 오류라고 보지는 않는다.
- 거래 `10161`은 54,000원 입금, 2,000원 환불, 배분 0원, 묶음·분류 지정이다. 유효 직접 귀속 잔액은 52,000원이다. 54,000원을 전부 직접 귀속한 뒤 2,000원 환불까지 별도 잔액 사용으로 가져오면 원입금 한도를 넘는다.
- 9월에는 소유자 후보가 없는 미귀속 잔액 거래도 1건 있다. 적요의 이름만으로 회원을 지정하지 않는다.

### 2.4 현재 이상이 없는 부분과 확인 범위

조회 당시 전체 배분에서 원입금/부과 없는 행, `payment` 외 종류, 출금에서 납부한 행, 납부 합계 캐시 불일치, 취소·면제 부과의 남은 배분, `배분 + 환불 > 원입금`은 각각 **0건**이다. 기존 기록을 그대로 이관할 수 있는 중요한 근거다.

현재 `deferred_to`가 남은 부과와 발행 대기 초안도 0건이다. 과거 이월·면제·연결 해제 감사 이력은 있지만 **감사 이력의 금액을 새로운 돈으로 만들어서는 안 된다.** 과거 이월 기능의 ‘정산=면제’를 받은 돈으로 해석하지 않는다.

공개 장부 함수 결과에서 7·8·9월 모두 항목 순액 합과 통장 수입−지출 차이는 0원이었다. 다만 운영진과 공개 장부의 항목 표시 방식까지 같다는 뜻은 아니다. 이번 조회는 동시 환불·배분의 안전성을 검증한 것도 아니다.

## 3. 처음부터 만든다면 나눌 데이터

기존 `status`, `deferred_to`, 거래의 여러 귀속 필드에 새로운 뜻을 계속 추가하는 방식은 피한다. **발행된 의무, 납기, 실제 입금의 사용처**를 각각 저장한다. 기존 은행 수집·중복 방지와 원거래 ID는 활용한다. 아래 이름은 설계용 가칭이다.

| 구성 | 저장할 사실과 역할 |
| --- | --- |
| `bank_transactions` | 실제 입출금 원본. 기존 ID·금액·일시·중복 방지 키 유지. 취소·이월로 가상 거래를 만들지 않음 |
| `billing_groups` | 월 회비·회차 대관·수동 모임의 안정된 ID. 발생일, 종류, 명칭. 회차와 부과 식별을 표시 문자열에서 분리 |
| `charge_issues` / `charge_items` | 발행 단위와 회원별 확정 의무. 원월·금액·발행 시각·발행 당시 계산 근거, 취소 이력과 이전/후속 부과 관계. 발행된 금액은 덮어쓰지 않음 |
| `due_slices` | 한 부과의 남은 의무를 납기별로 나눈 금액. 미납 일부 이월 지원. 합계가 원부과 잔여 의무와 일치 |
| `receipt_positions` | 원입금에서 아직 납부·환불에 쓰지 않은 금액의 구간. 소유자, 금액, 용도(`unassigned/member_pending/carry/refund_pending/club`), 사용 시작 월, 직접 귀속 묶음. 일부 금액만 이월하려면 구간을 분리 |
| `payment_allocations` / `allocation_reversals` | 어느 원입금 소유자의 돈을 어느 부과·납기분에 사용했는지와 그 해제 이력. 삭제 대신 원배분을 참조한 취소 금액 기록 |
| `refund_links` | 실제 출금과 원입금의 연결. 1차로 출금 하나→원입금 하나, 같은 원입금의 여러 부분 환불 허용. 출금 전 예약은 `refund_pending` 구간 |
| `settlement_operations` / `carry_lines` | 취소 후 발행·이월·납부·환불 처리의 요청 ID, 사유, 처리자, 시각, 영향받은 원내역과 전후 금액. 한 이월 작업에 미납 이동과 입금 이동을 함께 기록 |

`receipt_positions`는 잔액의 현재 위치를 나타낸다. 사용·분할·합침에 따른 변경은 작업 이력에 남기고, 현재 금액 0이 된 구간도 참조가 있으면 삭제하지 않는다. 납부/환불 이력은 소비한 구간과 원입금 ID를 함께 참조한다. 전체 테이블을 이벤트 재생 방식으로 만들 필요는 없지만, 금융 연결을 삭제해 이력을 잃는 동작은 없앤다.

회원·회차 삭제가 부과와 배분의 연쇄 삭제로 이어지지 않도록 새 금융 참조에는 삭제 제한 또는 보존되는 별도 식별자를 사용한다. 현재 프로필·회차 정보와 발행 당시 대상·금액의 근거를 분리해, 프로필 변경이나 일정 수정만으로 기존 의무가 재계산되지 않게 한다.

**부과 대상과 돈 소유자는 다를 수 있다.** 게스트 대신 A가 낸 돈을 해제하면 A의 잔액으로 돌아간다. 게스트 초대자나 현재 부과 대상이 바뀌었다고 소유자가 바뀌지 않는다. **설계 시 검토했던 여러 소유자의 입금 분할은 이번 구현에 포함하지 않았다.** 현재는 한 원입금의 소유자를 한 명으로 유지하며 여러 대납 대상에게 사용할 수 있다. 기존에 여러 소유자로 해석되는 배분이 있으면 이관을 중단한다(조사 당시 0건).

### 반드시 서버에서 지킬 계산

```text
원입금액
  = 유효 납부 배분 + 실제 연결 환불
  + 미귀속 잔액 + 회원 처리 대기 + 미사용 이월금 + 환불 예약 + 클럽 직접 귀속

원부과 미납 = 모든 납기분의 남은 의무 합계
유효 배분 = 최초 배분 − 그 배분에 대한 해제 금액 합계
```

모든 금액은 원 단위 정수이며 구간별 잔액은 음수가 될 수 없다. 신규 부과에는 남은 의무를 넘겨 배분하지 않고, 초과 입금은 잔액 구간에 남긴다. 취소된 부과의 현재 미납·유효 배분은 0이며 과거 납부·해제 이력은 보존한다.

이월금은 **돈의 새 종류가 아니라 원입금 잔액의 사용 시점 지정**이다. 미납 이월은 납기분의 이동이며 현금 보존식에 들어가지 않는다. 화면과 확정 작업은 하나지만 두 종류의 원자료를 부호 하나의 잔액으로 합쳐 저장하지 않는다.

## 4. 주요 작업의 구현 계약

### 4.1 취소 후 발행

`preview_replace`가 기존 부과·납부·납기·원입금 소유자를 읽어 해제액, 새 부과와 사용액, 남은 돈, 추가 미납을 보여준다. `replace_charges`는 같은 내용을 최신 상태에서 재검증하고 **한 DB 트랜잭션**으로 반영한다.

1. 선택한 기존 부과만 취소한다. 같은 묶음의 미선택 회원은 유지한다.
2. 그 부과의 유효 배분만 해제해 원입금 소유자의 잔액으로 돌린다. 같은 입금의 다른 부과 배분·기존 클럽 귀속은 유지한다.
3. 새 ID로 발행하고 이전 부과와 연결한다. 남은 납기 이월이 있었다면 새 부과에 승계할 납기·금액을 미리 확인한다.
4. 확인한 돈을 새 부과에 사용한다. 부족분은 미납, 잔액은 처리 대기/선택한 이월·환불 대기다. 명단 변경으로 다른 사람의 의무에 쓰는 경우 대납 대상을 명시해야 한다.
5. 실패하면 취소·발행·돈 사용 전체가 반영되지 않는다. 성공 이후 되돌릴 때는 새 이력으로 처리한다.

**혼합 입금 예:** 54,000원 중 회식 납부 30,000원 + 클럽 귀속 24,000원이 있다. 회식을 취소하고 24,000원으로 발행하면 `새 납부 24,000 + 클럽 귀속 24,000 + 회원 잔액 6,000 = 54,000`이어야 한다. 현재처럼 ‘거래 나머지는 전부 묶음 수입’으로 매번 계산하면 풀린 6,000원까지 클럽 수입에 흡수된다. 명시적 잔액 구간이 필요한 이유다.

현재 회원×월/회차/수동키 유일 제약은 취소 행에도 적용된다. 따라서 기존 `INSERT ON CONFLICT`를 그대로 쓰면 취소 후 새 발행이 막힌다. 새 모델에서는 발행 ID와 회원별 부과 ID를 별도로 두고, 묶음·회원의 현재 부과 연결 및 발행 요청 키로 중복을 막는다. **취소로 현재 부과가 없어져도 규칙 실행 이력은 남겨** 자동 생성기가 다시 발행하지 못하게 한다. 의도한 재발행만 새 요청으로 허용한다.

### 4.2 한 번의 이월 확정

`move_settlement(member_id, target_ym, debt_lines, money_lines, request_id)`처럼 회원별 미납과 돈을 한 요청에서 받는다. 미리보기와 확정 모두 서버가 동일한 산식을 사용한다.

- 미납 30,000원 중 10,000원 이동: 기존 부과의 납기분을 20,000원/10,000원으로 나눈다. 부과 합계와 총 미납은 변하지 않는다.
- 원입금 잔액 6,000원 중 4,000원 이동: 4,000원을 `carry`로, 2,000원을 기존 용도로 둔다. 이월한 구간에 사용 시작 월을 저장한다.
- 대상 월 도래 후 자동 적용은 기획의 권장 상세안이다. 채택하면 발행·이월 확정·월 전환 작업이 공통 `apply_available_funds`를 호출한다. 조회는 쓰기를 일으키지 않는다.
- 자동 적용은 해당 소유자 본인의 도래한 의무에 납기순으로, 돈은 원입금 순서로 한다. 같은 순위는 ID로 정렬한다. 미래 월 구간·환불 예약·클럽 귀속은 제외한다.
- 월 전환 작업은 재시도해도 같은 배분이 중복 생성되지 않아야 한다. 납기가 남은 미납은 자동으로 다음 달에 밀지 않는다.
- 일부 사용 후에는 미사용 구간만 이동·취소한다. 사용한 돈을 다시 옮기려면 해당 배분을 해제하는 결과를 함께 확인한다. 이 처리 중 자동 적용이 같은 돈을 다시 가져가지 않게 한다.

### 4.3 환불과 대납

원입금 검색은 월 제한을 없애고, 서버에서 **모든 달의 사용·환불·예약을 뺀 잔액**을 반환한다. 소유자가 확인된 회원 잔액 또는 명시적으로 해제한 귀속액만 환불에 사용한다.

환불 대기는 돈 사용을 예약할 뿐 출금이 아니다. 실제 출금과 연결할 때 예약을 소비하고 원입금과 출금 양쪽에 추적 관계를 남긴다. 이미 부과에 사용한 돈이라면 부과 취소 후 발행 또는 잘못된 납부 연결 해제가 먼저 필요하다.

환불 연결을 잘못 붙인 경우 원출금이 사라지지는 않는다. 다른 원입금/지출 용도로 재연결하는 작업과 잔액 해제를 함께 검증한다. 단순 연결 해제 후 사용처 미정인 실제 출금을 남기는 동안에는, 해당 금액을 자동 이월 사용 대상으로 즉시 풀지 않는 안을 권장한다.

회원 검색·대납 선택은 회원 ID를 사용한다. **돈 소유자 변경과 낼 사람 추가는 다른 입력**이다. 취소 시에도 그 구분을 보존한다. 동명이인 문제를 새 잔액 테이블에서도 이름 비교로 풀지 않는다.

### 4.4 동시성·권한·알림

- 모든 금액 사용 경로가 같은 원입금 잠금을 사용해야 한다. 환불·자동 적용·수동 배분·부과 취소가 서로 다른 검사를 통과해 중복 사용하지 않도록 원입금과 부과/납기분을 정해진 순서로 잠근 뒤 다시 계산한다.
- 요청 ID에 유일 제약을 두고 요청 내용과 결과를 저장한다. 같은 키의 재전송은 기존 결과를 돌려주고, 같은 키의 다른 내용은 거부한다. 미리보기 이후 잔액이나 부과가 바뀌면 확정 시 충돌 결과를 반환한다.
- 회원 화면은 자기 의무·잔액·대납 내역만 읽는다. 운영진 쓰기는 공통 RPC를 통하게 하고, 직접 테이블 쓰기 및 예전 RPC로 검증을 우회하지 못하게 한다.
- 알림은 성공한 작업과 연결된 한 번의 후속 처리로 발송한다. 이관·그림자 계산은 알림을 보내지 않으며, 자동 납부 적용보다 먼저 미납 독촉이 발송되지 않게 한다.

## 5. 조회와 화면을 구현하는 방식

서버가 `회원 정산 / 묶음 정산 / 월 통장 장부`를 각각 일관된 결과로 반환하게 한다. 카드·상세·회원 화면에서 미납, 이월, 직접 귀속을 다시 다른 방식으로 계산하지 않는다.

| 조회 | 기준 |
| --- | --- |
| 회원 정산 | 원월과 무관한 유효 의무·납기분, 소유한 잔액, 이월 사용액과 환불. 과거에 낸 날짜와 현재 사용한 부과를 함께 표시 |
| 묶음 정산 | 해당 묶음의 현재 부과·납부와 직접 귀속, 관련 실제 지출을 월 제한 없이 집계. 수납·지출·발행 확인 상태를 별도 표시 |
| 월 장부 | 원입출금 KST 월. 현재 유효 배분과 잔액 구간으로 각 거래 금액을 한 번씩 분류. 과거 월 재집계 허용 |

월 장부 수입 합은 원입금, 지출 합은 실제 출금이어야 한다. 환불은 실제 출금월에 표시하고, 입금과 같은 달이면 순액으로 보여주더라도 내부 입출금 합을 보존한다. 이미 반환된 원입금 부분은 ‘환불된 입금’ 등 추적 가능한 분류로 남겨 돈의 사용·잔액과 장부 표현을 혼동하지 않는다. 이전 달 입금 사용을 당월 수입으로 다시 더하지 않는다.

공개/운영진 장부는 동일한 서버 집계를 사용하고 공개 범위만 다르게 한다. 회차·동명이인 식별 개선은 이 결과에 ID와 구분용 정보를 실어 구현한다.

## 6. 기존 운영을 끊지 않는 전환 순서

| 단계 | 구현 내용 | 통과 조건 |
| --- | --- | --- |
| 1. 기존 상태 기준선 | 전체 원거래·부과·배분·환불·귀속·취소 상태와 ID 관계를 일관된 시점에 추출. 이 문서의 집계 SQL은 진단용이고 전체 백업은 별도 | 7·8월 완료분, 9월 진행분, 과거 월 연결이 모두 포함됨 |
| 2. 새 도메인과 이관기 | 새 테이블·공통 RPC·조회, 기존 ID→새 ID 매핑과 반복 실행 가능한 이관기 작성 | 전환만으로 의무·납부·잔액이 변하지 않음. 이관 실행이 운영 발행이나 알림을 호출하지 않음 |
| 3. 기존 자료로 대조 | 복제한 데이터에서 새 집계를 실행해 회원/부과/원입금별 차이를 확인 | 차이가 있으면 ‘새 부과 생성’과 ‘기존 표시 오류 수정’을 구분한 목록 확보 |
| 4. 새 기능 검증 | 취소 후 발행·이월·환불을 별도 DB에서 검증. 필요한 UI를 같은 서버 계약으로 연결 | 아래 시나리오와 실제 이관 예외 통과 |
| 5. 전환 | 회계 쓰기를 잠깐 멈추고 최신 상태 재이관/차이 반영·대조 후 새 API로 일괄 전환 | 구 API·직접 쓰기·자동 생성 트리거까지 새 규칙으로 연결되거나 차단됨. 새 쓰기 시작점 기록 |
| 6. 운영 확인 | 과거 납부·현재 미납·이월 잔액·환불 결과 확인 후 구 구현 정리 | 새 쓰기 이후 되돌릴 경우 그 작업까지 보존하는 복구 절차 확보 |

월별로 구/신 엔진을 나누면 같은 원입금이 두 엔진에서 쓰일 수 있다. 읽기 비교를 병행하는 것은 가능하지만, 실제 금액을 사용하는 엔진은 전환 시점에 하나로 맞춘다.

이관의 구체 규칙:

- 기존 부과와 배분을 **발행된 사실로 복사**한다. 404건의 완납을 `paid` 플래그만 복사하지 말고 원입금과 연결된 금액으로 재현한다. 복사한 캐시와 배분 합을 대조한다.
- 7·8월 미납 4건은 기존 상태를 유지한다. 의도 확인 후 필요하면 별도 취소/면제로 처리한다. 7·8월 취소 3건은 다시 발행하지 않는다.
- 과거 부과가 없는 회원도 현재 규칙으로 채우지 않는다. 기존 묶음은 전환 이전 발행 검토가 이루어진 범위로 기록하고, 누락 의심 건은 명시적 추가 발행에서만 다룬다.
- 원입금마다 배분·누적 환불을 먼저 복원하고, 남은 금액을 기존 귀속과 소유 근거로 구간화한다. 근거 없는 잔액은 미귀속으로 유지한다. 이월 시작 월을 임의로 채우지 않는다.
- 배분 납부자와 `paid_by`가 다르거나 한 원입금의 소유자가 여럿인 예외는 자동 추측하지 않는다. 현재 조회에는 없지만 전환 직전 다시 검사한다.
- `deferred_to`가 새로 생겼다면 기존 의무의 남은 금액과 납기로 옮긴다. `waived/void`를 입금 이월로 변환하지 않는다. 초안이 새로 생겼으면 공개하지 않은 초안으로 옮기고 재검증한다.
- 과거 계산 근거가 없는 곳에는 ‘기존 시스템 발행분’으로 표시한다. 오늘의 참석자·가입일·단가로 과거 근거를 꾸며내지 않는다.
- 삭제된 과거 부과/배분은 현재 테이블만으로 완전 복원할 수 없다. 감사 이력은 보조 근거이며 이관하면서 자동 복원하지 않는다.

전환 시 특히 교체할 현재 쓰기 경로는 대관 총액 변경의 배분·부과 삭제, 수동 부과 upsert/delete, 비활성·명예 지정의 과거 회비 삭제, 이월 정산의 면제, 입금 전체 배분 삭제, 회차 종료·월 진입의 자동 발행, 직접 거래 귀속과 환불 RPC다. 화면 버튼만 바꾸면 다른 경로가 새 데이터 계약을 깨뜨릴 수 있다.

주요 근거는 [대관 총액 변경](../supabase/migrations/20260823080000_reset_session_court_on_fee_change.sql), [비활성화 시 삭제](../supabase/migrations/20260820020000_uncharge_dues_on_deactivate.sql), [배분 확정](../supabase/migrations/20260823110000_reconcile_manual_batch_path.sql), [현재 월 장부](../supabase/migrations/20260823050000_batch_txn_link.sql), [회원 잔액 조회](../supabase/migrations/20260824000000_my_refund_pending.sql)다. 전체 현행 동작과 다른 경로는 [현행 명세](ACCOUNTING_SPEC.md)에 정리되어 있다.

새 데이터 쓰기 시작 전에는 구 시스템으로 복귀할 수 있다. **새로운 부분 이월·취소 이력이 생긴 뒤에는 구 컬럼으로 무손실 역변환이 보장되지 않는다.** 이번 구현은 그 이후에도 전체 복귀할 수 있도록 새 처리 이력·백업을 보존하고 기존 원장을 다시 사용한다. 새 금융 결정은 기존 기능에 자동 역이관하지 않으며, 실제 통장 거래와 대조해 재처리한다. 직전 작업 복구와 전체 복귀의 차이는 [적용 문서 §4](ACCOUNTING_ROLLOUT.md#4-문제-발생-시-복구)를 따른다.

| 8월 30,000원 완납 → 취소 → 24,000원 발행 → 6,000원 이월 | 원입금 보존, 새 부과 완납, 미사용 이월 6,000원. 9월 입금 추가 없음 |
| 위 잔액으로 9월 5,000원 회비 납부 | 새 배분 5,000원, 남은 돈 1,000원. 부과 미납과 잔액을 이중 차감하지 않음 |
| 54,000원 혼합 입금에서 회식만 취소 후 발행 | 클럽 귀속 24,000원 유지, 반환된 6,000원이 회원 잔액으로 남음 |
| 8월 미납 5,000원 + 입금 잔액 6,000원 + 9월 회비 5,000원 | 적용 후 총 미납 4,000원. 기존 의무나 원입금 복제 없음 |
| 미납 30,000원 중 10,000원만 다음 달로 이동 | 원부과 하나, 납기분 20,000원/10,000원. 일부 납부 후 정확한 납기분 잔액 |
| 이월 사용 예정일 전 조회·월 전환 재시도 | 조기 사용 없음. 도래 후 실제 부과에 한 번만 사용 |
| 같은 돈에 취소·자동 사용·환불 동시 요청 | 원입금 한도 보존, 중복 성공 없음, 실패 시 중간 상태 없음 |
| 취소 후 발행 도중 오류·요청 재전송 | 전체 미반영 또는 최초 성공 결과 반환. 이중 발행·이중 알림 없음 |
| 대납한 부과 취소, 동명이인 회원 전환 | 실제 돈 소유자에게 복원, 다른 사람의 잔액·납부 이력이 섞이지 않음 |
| 귀속 입금 54,000원 중 2,000원 이미 환불 | 환불과 직접 귀속 52,000원으로 원입금 보존. 회원 이월금 52,000원 생성 금지 |
| 기존 회원 비활성·명예 지정·회차 금액 변경·옛 클라이언트 요청 | 보존한 과거 부과/배분이 삭제되지 않고 새 공통 작업 계약을 따름 |
| 모든 월 장부 재조회 | 항목 분류 변경 허용. 각 원거래를 한 번만 세고 수입·지출 합은 실제 거래 합과 일치 |

이번 검토에서는 운영 데이터 집계와 네 핵심 함수의 배포 본문 대조까지 수행했다. 이후 별도 로컬 PostgreSQL에서 수행한 통합·상태 충돌·복구 검증 결과는 [적용 문서 §5](ACCOUNTING_ROLLOUT.md#5-검증-결과와-범위)에 기록했다. 실제 다중 연결 잠금 경쟁과 배포 환경의 예약 실행은 별도 확인 범위다.

## 8. 구현 전 남은 정책 선택

이미 확정된 방향은 **부과 취소 후 발행**, **미납과 받은 돈의 이월 통합**, **과거 월 장부 재집계 허용**이다. 월 마감 보존 정책을 추가로 정할 필요는 없다.

남은 것은 이월금 자동 사용 여부·우선순위, 기존 미납 4건의 업무상 처리, 기존 미귀속 잔액을 환불/이월 중 무엇으로 정할지, T01 회차 시간 표시 조건이다. 현재 상태 그대로 이관하는 설계는 이 선택 전에 진행할 수 있다. 자동 사용은 기획의 권장 상세안으로 유지하며 기존 잔액에 소급 적용하지 않는다.

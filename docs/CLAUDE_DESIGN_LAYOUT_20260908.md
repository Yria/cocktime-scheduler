## 화면 변경

- 현황: 회비와 대관·모임을 카드 단위로 대조한다. 완납·미납·이월 또는 제외 인원을 분리하고, 기존 참석·부과 제외 사유와 납부 근거를 유지한다. 발행되지 않은 대상을 미납으로 계산하지 않는다. 일반 정산 조작은 해당 탭으로 이동해 수행한다.
- 정산함: 원본 2b처럼 납부자 이름·변경 버튼 → 배분 막대·잔액 → 부과 선택 칩 → 전체 너비 확인 버튼 순서로 배치한다. 매칭된 입금은 카드 자체를 펼칠 필요 없이 바로 확인한다. 미매칭·동명이인은 카드 안에서 이름·년생으로 선택한다. 금액 조정·메모·대납·이월·용도 지정·환불 및 같은 입금의 다른 분할 잔액은 정산 옵션에서 기존 기능으로 연결한다. 거래 검색은 기존 기능을 유지하기 위해 상단에 남겼다.
- 회계: 월 수입·지출 요약 아래 같은 항목의 수입·지출을 한 행에서 비교한다. 금액 열을 고정하고 필터를 줄바꿈해 표시한다. 하단 전체 거래 내역과 기존 연결 해제·환불 취소 경로는 유지한다.
- 부과: 탭을 열면 즉시 종류·이름·발생일 / 명단 / 계산 방식 / 합계·발행의 기본 전표를 표시한다. `지난 명단`에서 기존 회차의 참여자·식사 명단을 가져온다. 총액 분할·인당 직접 입력과 올림 단위, 명단의 선택·제외는 로컬에서 계산한다. `N명에게 발행`으로 기본 전표를 확정한다. 개별 금액·분할 납기는 부과 옵션에서, 기존 부과 내역·회비·대관 및 이월은 하단 관리 링크에서 접근한다.

## 원본과 현재 기능의 차이

1. 원본의 통장 거래 전체에 대한 `취소됨` 상태는 현재 데이터 모델에 없다. 납부 연결 해제와 환불 취소를 각각 제공하며, 원본 통장 거래는 보존한다. 목업처럼 거래 자체에 취소선을 긋지 않았다.
2. 서버가 마지막 통장 동기화 시각을 반환하지 않는다. 이번 화면에서 가져오기와 새로고침이 성공한 시각만 표시한다.
3. 수동 JSON 백업 내보내기는 후속 사용자 요청으로 제거했다. 전환·롤백 시 자동 복구 백업은 별도 내부 경로로 유지한다.
4. 원본의 자동 배분과 회원 잔액 보관 예시는 샘플 동작이다. 앱은 기존의 확실한 단일 후보 제안과 잔액 처리 규칙을 유지한다. 남는 돈의 이월·용도 지정이 필요하면 해당 기존 기능으로 처리한다.

## 정산함 재점검 및 보정

사용자의 재점검 요청으로 원본 2b와 실제 화면을 다시 비교했다. 앞선 구현은 기존 처리 방식 버튼, 항상 보이는 회원 검색, 금액 입력·메모·대납 체크박스와 중복 확인 요약을 남겨 원본의 짧은 전표 구조를 충분히 반영하지 못했다.

- 기본 전표에서는 처리 방식 선택 행과 상세 입력을 제거하고, 배분 항목을 짧은 칩으로 표시한다. 선택된 항목은 기존 디자인 시스템의 반전 색을 사용한다.
- 납부자 이름이 카드 제목이 되고 은행 입금자명은 보조 정보로 표시된다. 변경 시 년생/ID로 동명이인을 구별하며, 선택하면 카드 안의 납부 항목으로 이어진다. 키보드 포커스는 변경 버튼으로 돌아온다.
- 세부 작업은 상단 `…`(접근명 `정산 옵션`)로 연다. 기본 납부 확인에는 모달이나 추가 확인 단계를 요구하지 않는다. 부과별 금액 수정·대납 확인·메모 및 이월/용도/환불 경로는 유지한다.
- 기존 환불 원입금 선택기의 `.ac-receipt`와 충돌하지 않도록 정산 전표 컨테이너에는 `.ac-inbox-receipt`를 사용한다. 확인 버튼이 카드 너비를 채우는지 별도로 검증한다.
- 새 DB 호출이나 회계 명령을 추가하지 않았다. 서버 검증, 납부자 재지정 제약, 중복 확정 방지, 응답 유실 재시도는 기존 흐름을 재사용한다. 운영 데이터와 과거 월 회계는 수정하지 않았다.
- 원본의 샘플 자동 배분·회원 잔액 보관을 새 금융 로직으로 옮기지 않았다. 기존의 확실한 단일 후보 제안만 자동 선택하고 나머지는 사용자가 선택한다. 회계 원장의 기존 상세 편집과 취소 기능도 유지한다.

## 부과 화면 원본 2d 반영

정산함 보정 후 사용자가 부과 화면도 같은 디자인으로 요청하여 원본 2d를 MCP 미리보기로 다시 확인했다. 기존 색상·폰트·반경·입력·칩·선택 색 토큰을 그대로 사용하고 전표 구조와 기본 진입 경로를 맞췄다.

- 첫 화면의 발행 메뉴와 별도의 `새 수동 부과` 진입 단계를 기본 전표로 바꿨다. 원본처럼 종류·이름·발생일, 선택 명단, 계산 방식과 금액, 인당 금액·합계, 전체 너비의 발행 버튼이 순서대로 이어진다.
- 참고 회차 폼은 상단 `지난 명단`에서 연다. 실제로 가져온 회차와 인원을 명단 아래 표시한다. 기존에 선택한 회원은 유지하고 중복 회원 ID는 추가하지 않는다.
- 이름·초성·년생 검색과 선택 상태는 서버 호출 없이 처리한다. 동명이인은 년생 또는 ID로 구분한다. 제외한 사람은 명단에서 지우지 않고 선택 해제·취소선으로 표시한다.
- 기본 전표의 총액·명단·올림 계산은 기존 `updateManualLines`를 재사용한다. 발행 요청도 기존 `issue` 명령과 `useInlineAccounting`의 검증·재시도 경로를 사용한다. 기본 전표는 필수 처리 사유 입력과 별도 서버 미리보기 화면을 제거하고 `N명에게 발행` 한 번으로 확정한다. 비워 둔 처리 사유에는 부과 이름·인원을 기록하며, 메모를 직접 입력할 수도 있다.
- 발행 시도 후 응답이 유실되면 입력과 다른 조작을 잠그고 동일 요청 ID로 결과만 재확인한다. 상세 부과·취소 후 발행·분할 납기 등의 기존 미리보기 흐름은 유지한다.
- 부과 옵션에는 게스트·비활성 회원, 개별 금액·납기, 처리 사유, 입력 초기화를 둔다. 기존 발행 내역·회비·대관 부과·미납 및 입금 이월은 하단 관리 링크로 연결했다. 초안은 다른 탭과 발행 내역을 다녀와도 유지한다.
- 원본의 샘플 회원·금액·발행 완료 토글은 실제 운영 사실로 사용하지 않는다. 실제 명단을 고르거나 가져오기 전에는 대상 0명이고 발행은 비활성이다. 실제 발행 후에는 완료 안내를 표시하며, 취소·복구는 기존 관리 기능에서 수행한다.

사용자 요청 두 건을 반영했다. "회원 화면도 홈 톤으로", "합계가 이상한데 확인좀".

(accounting.css §11)로 바꿨다. 같은 날 병행 작업이 그 래퍼에 "항목별 수지 시트와 아래
거래 내역 표를 한 장으로 잇는" 스킨 규칙(D20: 시트 하단 테두리·모서리 제거)을 달았는데,
거래 내역 표가 없는 회원 화면에 그대로 붙으면 **시트 바닥이 열린 채로 끝난다.**
기하(94/80 열·12px 패딩)는 같은 값으로 복제했고 두 화면은 이제 서로 독립이다.

**합계.** 숫자가 틀린 곳은 없었다 — 서버 불변식 `dues_assert` 가 살아 있는 부과마다
`부과액 = Σ 납기 잔액 + Σ 배분(해제 제외)` 을 매 명령마다 강제하므로 카드의
`낸 돈 + 남은 금액 = 부과` 는 깨질 수 없다. 이상한 것은 **합계라는 기호를 쓴 자리**였다.

- 카드의 마지막 줄 `남은 금액` 이 `.ac-total`(3px 이중선 + 20px = 이 화면의 합계 기호)을
  입고 있었다. 위 줄들의 합은 히어로의 '낸 돈'(5,000 + 18,000 = 23,000)인데 그 자리에
  6,000 이 앉아 "5,000 + 18,000 = 6,000" 처럼 읽혔다. 원본 3a 가 `.ac-total` 을 쓴 자리라
  그대로 옮겼던 것이고, 이번에 합계 기호를 걷어 냈다(`.ac-mine-rest`: 굵은 1px 만).
  `accounting.css:314` 의 "크기와 이중선은 한 세트 — 이중선 없이 20px 을 쓰지 않는다" 를
  지키는 쪽은 20px 을 쓰지 않는 것이다.
- 납부 내역의 `합계` 는 진짜 합이라 기호를 유지하되, **줄이 하나면 합계 줄을 생략한다.**
  같은 수가 바로 위에 또 있으면 합계가 고장 난 것처럼 읽힌다(1건인 실제 fixture 에서
  30,000 이 두 번 나왔다).
- 알림 문장의 주어를 `지금 낼 돈 N원` 으로 바꿨다. 카드의 `남은 금액` 은 **그 달**,
  알림은 **달을 넘는 오늘 기준**이라 두 수가 다를 수 있는데(8월 카드 남은 0 · 알림 7월
  회비 2,000), 라벨이 없으면 이것도 "합계가 안 맞는다"로 읽힌다. 조사는 `subjectJosa()`
  로 붙인다(`회비가` / `2건이` / `2,000원이`).
- 미터는 `(부과−남은)/부과` 대신 화면에 쓴 '낸 돈'을 그대로 그리도록 묶고 100% 로 자른다.

검증: 회계 브라우저 35개, 유닛 634개, `tsc -b` + Vite build, 변경 파일 ESLint 통과.
라이트·다크·클럽 탭 캡처를 다시 떴다(`test-results/design-my-dues-*.png`).
같은 시간대에 다른 세션이 정산 카드·원장을 편집 중이었고, 그 중간 상태에서 e2e 4건이
실패했다가(임시 TEMP 테스트 2건 포함) 그쪽 정리 후 35개 전부 통과로 돌아왔다.

#### 컴포넌트 정리 (2026-09-11, 4차 후속)

4차에서 껍데기는 하나로 모았지만 **행 마크업이 세 곳에 복붙**돼 있었다(배분 · 환불로
나간 몫 · 처리 끝난 출금). `TransactionCard` 안에 프리미티브 셋으로 접었다.

| 조각 | 책임 | 사용 |
| --- | --- | --- |
| `SettledList` | 처리 내역 묶음. 방향으로 접근명만 갈린다 | 2곳 |
| `SettledRow` | 3단 골격 + 금액 활자. 겹치는 것만 정한다 | 3곳 |
| `SettledWho` | 좌측 첫 줄 `[배지] 대상` | 3곳 |

자리마다 다른 부분은 슬롯 prop 이 아니라 **children 합성**으로 받는다 — 배지가 붙는지,
이름인지 출금 번호인지, 근거 줄이 있는지가 전부 호출부의 조합이라 행 종류가 늘어도
프리미티브에 prop 이 늘지 않는다. `actions` 만 prop 인 이유는 children 과 **다른 칸**
(우측 레일)에 들어가서다. `.ac-allocation*` · `.ac-settlement-history` 클래스는 이제
각각 정확히 한 곳에서만 쓰인다.

검증: 회계 브라우저 35개(`--trace off`), 유닛 620개, `tsc -b` + build, Biome 통과.
렌더 결과는 리팩터링 전과 동일함을 캡처로 대조했다.

> 이 시점 e2e 전체 실행이 무작위로 1~2건 실패했는데 전부 단언이 아니라
> `ENOENT … /test-results/.playwright-artifacts-*/…trace` 였다. 같은 저장소에서 다른
> 세션이 동시에 Playwright 를 돌리며 `test-results/` 를 비우는 충돌이다.
> `--trace off` 로 35/35 통과(53.5초)를 확인했다 — 코드 회귀가 아니다.

#### 빈 달 점선 박스 · 합계 띠 (2026-09-11, 같은 날 3차)

실기기 확인에서 나온 지적 두 건. 둘 다 실측으로 원인을 잡았다.

- **빈 달의 점선 박스가 머리글 선에 붙어 있었다.** 실측: 좌우 16 · 아래 14 · **위 0**.
  테두리 있는 박스가 다른 선에 맞닿으면 두 선이 한 덩어리로 읽힌다. 위 간격을 그
  컨테이너의 안쪽 여백과 같게 맞췄다 — 카드 패딩이 톤마다 다르므로(장부 12 · 홈 14)
  `var(--ac-surface-pad, var(--ac-s-3))` 로 같은 값을 되받는다. 클럽 회계 탭의 빈 달도
  같은 규칙으로 8px(그 컨테이너의 여백) 띄웠다.
- **합계 띠가 잘린 조각처럼 보였다.** 실측: 시트 안에서 좌우 25px 씩 들어와 끝났다.
  운영진 쪽은 이미 같은 지적을 D18(`accounting-home.css`)로 고쳤는데 그 규칙이
  `.ac-ledger-page` 스코프라, 회원 탭을 `.ac-mine-ledger` 로 분리한 순간 회원 화면만
  풀블리드를 잃었다 — **이번 분리가 만든 회귀다.** 같은 기법을 회원 규칙에도 넣었다:
  음수 마진으로 상자만 시트 폭까지 넓히고 같은 값을 패딩으로 되돌린다. `width: auto`
  가 필수다(`.ac-row { width: 100% }` 때문에 안 넓어지고 왼쪽으로만 밀린다).
  실측으로 콘텐츠는 1px 도 안 움직였다(금액 열 우측 265 → 265, 349 → 349).
- 덤: `.ac-mine-list > div` 가 머리글(`.ac-sheet-head`)까지 잡고 있었다. 홈 톤에서는
  (0,3,0) 스킨 규칙이 이겨 드러나지 않았지만 장부 톤·인쇄에서는 머리글 패딩이 깨진다.
  `:not(.ac-sheet-head)` 로 좁혔다.

검증: 회계 브라우저 35개, 유닛 634개, `tsc -b` + build, 변경 파일 ESLint 통과.

#### 항목별 수지 → 거래 내역의 필터 줄 (2026-09-11, 같은 날 4차)

사용자 요청: "항목별 수지를 필터처럼 보이게 해서 거래내역 안에 넣되, 기존 버튼 형식은
너무 길고, 수입/지출은 볼 수 있어야 하고, 합계는 빼도 된다."

- **형태**: 상태 필터 줄 아래에 가로로 흐르는 **두 줄짜리 칩**(이름 / 수입·지출).
  실측 높이 51px — 15개 항목이면 표는 600px 을 넘었다.
- **순서**(사용자 선택): **종류 묶음 + 날짜순** — 대관비(회차 날짜) → 회비(월) →
  수동 묶음(발생일) → 묶음 없는 합성 항목(라벨순). 처음엔 `max(수입, 지출)` 내림차순
  으로 세웠는데 날짜가 흩어져 특정 회차를 눈으로 좇을 수 없었다. 서버(`dues_ledger`)는
  라벨 문자열순으로만 주고 종류·발생일은 `dues_groups` 에 있어 정렬은 클라이언트
  몫이다 — 규칙은 `sortLedgerBuckets`(lib)로 빼고 유닛 4개로 잠갔다.
- **열 정렬**: 칩 폭을 150px 로 고정하고 금액을 같은 폭의 두 칸에
  각각 오른쪽 정렬한다. 처음엔 0 인 쪽을 생략했는데, 그러면 칩마다 수입·지출이 자리를
  바꿔 앉아(회식은 지출이 첫 칸, 이월 입금은 수입이 첫 칸) 가로로 훑을 때 열이 서지
  않았다 — 표의 `—` 자리표시가 칩에서도 같은 일을 한다. 실측: 8개 칩 모두 수입 칸
  우측 73px · 지출 칸 우측 141px 로 동일하다. 이 줄의 본업은 대조이므로 폭 낭비보다
  열 정렬을 택했다.
- **누를 수 있는 것과 없는 것**: 묶음 ID 가 있는 항목만 버튼이다. 환불·미분류·이월
  입금처럼 좁힐 대상이 없는 합성 항목은 **점선 윤곽의 읽기 전용 칩**으로 남긴다 —
  금액은 읽혀야 하고, 눌러도 아무 일 없는 버튼을 두면 나머지 칩의 클릭도 못 믿는다.
  틴트 면(회색)을 쓰지 않은 이유: 바로 윗줄 상태 필터에서 회색은 '안 눌린 버튼'이라
  한 화면에서 같은 색이 두 뜻을 갖는다. 그래서 칩 줄도 `.ac-ledger-filters` 트랙을
  공유하지 않는다(홈 톤 D13 이 그 줄의 버튼을 무테두리 틴트로 덮는다).
- **합계 삭제**: 통장 카드가 이미 같은 수입·지출·순액을 말한다.
- **회원 화면은 그대로**: `/my-dues/ledger` 에는 거래 목록이 없어 항목별 합계를 볼
  자리가 그 시트뿐이다. `CashLedgerView` 에 `buckets` 프롭을 두어 운영진만 끈다.
- **조회는 그대로 1회**: 항목 줄은 통장 카드가 이미 받은 응답을 `onLines` 로 올려
  준다(콜백은 latest-ref 로 잡아 인라인 함수가 재조회를 부르지 않게 했다).
- **정리**: 같은 날 먼저 들어온 '항목 행 = 필터' 기능(행 버튼 + `aria-pressed` +
  두 시트를 한 장으로 잇는 홈 톤 D20)은 이 칩이 그대로 이어받는다. 행 버튼·D20·
  `.ac-ledger-item`·`.ac-ledger-chevron` 은 렌더되지 않는 죽은 코드가 되어 지웠다 —
  주석이 없어진 UI 를 설명하고 있으면 다음 사람이 그걸 믿는다.

검증: 회계 브라우저 35개(항목 칩 누름→1건, 해제→4건, 합성 항목은 버튼 아님을 단정하는
새 계약 포함), 유닛 634개, `tsc -b` + build, ESLint 통과. 라이트·다크 390px 에서 가로
스크롤 0.

# 팀매칭 모순·정합성 검토

> 검토일: 2026-09-07 · 기준: `30ddf07`에서 시작한 로컬 작업 트리.
> [현재 동작 기획](TEAM_MATCHING_SPEC.md)과 함께 읽는다. 기존 문서·TypeScript 코드·저장소의 최신 관련 SQL 정의를 대조했다. 운영 데이터 분석이나 DB 배포 상태 확인은 수행하지 않았다.
> 최초 검토는 문서·코드 대조로 수행했고, 후속 확인에서 R1·R2·R3 재현 검사를 추가했다(§5.1). 이후 R5 늦참 보완 SQL과 새 만남 보정, R9 점수 표시를 구현했다. SQL·앱 배포 전이며 다른 제품 로직의 수정 제안은 아직 구현하지 않았다. 기존 테스트 통과가 이 문제들의 부재를 뜻하지 않는다.

## 1. 판단 요약

현재 팀매칭은 **보드 수동 구성 + 점진적 자동편성 + 회원 파티**다. 핵심 선발 함수의 가중치와 상세 알고리즘 문서는 대체로 일치하지만, 상위 기획의 오래된 설명과 ‘항상·최우선·금지’ 같은 강한 표현이 실제 합산 비용 방식과 충돌한다.

실제 구현에서 우선 확인할 문제는 **경기 수정의 참가 자격 누락, 수정 후 경기 유형 불일치, 재동기화의 직전 유형 복구 누락**이다. 이들은 후보 순위와 경기 기록에 영향을 준다.

| ID | 우선순위 | 분류 | 발견 사항 | 확인 방법 |
| --- | --- | --- | --- | --- |
| R1 | 높음 | 구현 불일치·예외 정책 미정 | 경기 수정에서 휴식·콕 미확인·타팀 소속 선수를 편입 가능 | 휴식·미확인은 UI 렌더·실제 store·로컬 SQL 실행 확인. 타팀 소속은 정적 추적 |
| R2 | 높음 | 구현 불일치 | 선수 교체 후 성별 구성과 경기 유형·직전 유형이 어긋남 | 실제 store·DB 호출·로컬 SQL·완료 집계 실행 확인 |
| R3 | 높음 | 복구 누락 | 재연결 시 그룹 이력은 복구하지만 직전 경기 유형은 복구하지 않음 | 실제 초기 로드·resync에 같은 서버 응답을 넣어 차이 확인 |
| R4 | 중간 | 기획 표현 과장 | ‘경기수 최우선’, ‘2인 겹침은 1판을 못 뒤집음’이 일반적으로 성립하지 않음 | 실제 함수의 수치 반례 실행 |
| R5 | 중간 | 보완 완료·DB 적용 전 | 미합류자 평균 제외, 콕 체크 OFF의 추가·설정 전환 보정 | 보완 SQL 로컬 PostgreSQL 검증 11개 통과 |
| R6 | 중간 | 정책·명명 불일치 | 여성 포함 구성이 남복으로 기록되고 ‘허용’ 설정이 편성 금지는 아님 | 실제 유형 함수 실행·추천 비용 확인 |
| R7 | 중간 | 문서 누락·정책 분기 | 수동 추천에서만 경기 중 비용을 해제하는 예외가 있음 | 훅·자동편성 대조 및 비용 실행 |
| R8 | 중간 | 값 의미 불일치 | 미등급을 선발은 ‘정보 없음’, 페어는 ‘실력 0’으로 취급 | 실제 선발·페어 함수 실행 |
| R9 | 낮음 | 수정 완료·앱 배포 전 | 새 만남·대기·혼복수 열을 추가해 모든 계산 항목 표시 | `breakdown` 합계 검사·렌더 열 대조 |
| R10 | 중간 | 구현 오류 | 선수 집합이 같은 페어 변경은 수정 버튼을 눌러도 저장되지 않음 | 모달 스테이징·store 조기 반환 추적 |

‘높음’은 편성 자격·기록·기기 간 추천 정합성에 직접 영향을 주는 항목이다. 운영 환경에서 발생 빈도나 실제 피해 규모를 측정한 우선순위는 아니다.

## 2. 상세 발견 사항

### R1. 경기 수정이 일반 편성의 참여 조건을 우회

**기획 기준:** 휴식 선수는 편성에서 제외하고, 콕 체크가 켜져 있으면 확인 후 매칭에 참여한다. 타 예비팀의 정식 멤버도 일반 추천 풀에서 제외한다.

**실제:** `MatchEditModal.benchIds`는 원래 4명과 `status !== 'playing'`인 전원을 교체 대상으로 삼는다. `resting`, 콕 미확인, 다른 예비팀 소속을 검사하지 않는다. `handleSetMatchRoster`에도 해당 검증이 없고, `set_match_roster`는 추가된 선수를 그대로 `playing`으로 바꾼다. 다른 팀 소속 선수는 보드의 경기 중 anchor 정리 경로에서 원래 팀에서 빠질 수 있다.

**재현 조건:** 진행 중인 경기에서 ‘경기 수정’을 열고 휴식 선수 또는 콕 미확인 선수를 고른다. 현재 경로상 수정 요청은 일반 추천의 자격 검사 없이 전송·반영된다.

**영향:** ‘휴식하면 편성되지 않음’, ‘콕 확인 후 참여’라는 규칙이 조작 경로마다 달라진다. 운영진의 의도적인 예외 기능이라면 그 범위와 표시가 기획에 필요하다.

**제안:** 경기 수정에도 공통 자격 검사를 적용한다. 예외를 허용할 정책이라면 휴식 복귀·콕 확인·타팀 이동을 명시적인 동작으로 정의한다. 서버에서도 세션 소속·경기 중 여부·자격을 검증해야 최종 반영 시점의 상태를 보호할 수 있다.

근거: [일반 추천 풀](../src/lib/board/recommendPool.ts) `buildRecommendData`, [경기 수정 화면](../src/components/board/MatchEditModal.tsx) `benchIds`, [경기 액션](../src/store/sessionStore.ts) `handleSetMatchRoster`, [최신 경기 수정 SQL](../supabase/migrations/20260817020000_advisor_function_search_path.sql) `set_match_roster`.

### R2. 선수 교체 후 경기 유형과 추천 이력이 갱신되지 않음

**기획 기준:** 경기 유형은 현재 4명의 성별 구성으로 결정하고, 직전 또는 진행 중인 경기 유형을 로테이션에 사용한다.

**실제:** 경기 수정은 `teamA/teamB`와 선수 상태만 바꾼다. 요청·SQL에 새 `game_type` 계산이 없고, `handleMatchRosterUpdated`는 `lastGameType`을 갱신하지 않는다. 완료 RPC는 기존 `match.gameType`을 전달받아 혼복 판수를 집계한다.

**재현 조건:** 혼복(남2·여2)의 여성 1명을 남성으로 교체한다. 참가자는 남3·여1이 되지만 기존 혼복 유형이 유지된다. 완료 시 기존 혼복 분기를 따라 최종 남성 참가자들의 `mixed_count`가 증가한다. 성별을 유지하는 교체도 새로 들어온 선수의 진행 중 유형은 완료 이벤트 전까지 즉시 반영되지 않는다.

**영향:** 화면·기록의 유형이 실제 구성과 어긋나고, 이후 혼성/동성 로테이션 추천이 잘못된 이력을 사용할 수 있다. `W_MIXED=0`이므로 혼복 누적수 자체는 현재 선발 비용에 영향을 주지 않지만 기록 오류는 남는다.

**제안:** ‘최종 로스터 기준으로 집계한다’는 현재 방향을 유지한다면 수정 시 경기 유형도 원자적으로 갱신하고 이벤트에 포함한다. 새 참가자와 이탈자의 직전 유형을 어떤 기준으로 복원할지도 함께 정한다. 실제 진행된 경기의 최초 유형을 보존하려는 정책이라면 유형 분류·집계의 정의부터 별도로 명시해야 한다.

근거: [유형 결정](../src/lib/teamSelection/pairPlayers.ts) `determineGameType`, [경기 액션](../src/store/sessionStore.ts) `handleSetMatchRoster`·`handleComplete`, [이벤트 처리](../src/store/sessionBroadcastHandlers.ts) `handleMatchRosterUpdated`, [DB 호출](../src/lib/supabase/actions.ts) `dbSetMatchRoster`·`dbCompleteMatch`, [최신 SQL](../supabase/migrations/20260817020000_advisor_function_search_path.sql) `set_match_roster`·`complete_match`.

### R3. 재연결 복구에서 직전 경기 유형이 누락

**기획 기준:** 재연결·편집권 이양 후에도 현재 세션 상태와 추천 이력이 서버 상태로 복구되어야 한다.

**실제:** 초기 `snapshotToClientState`는 완료 경기를 종료 시각 순으로 처리한 뒤 진행 중 경기로 덮어 `lastGameType`을 만든다. 시작·완료 이벤트도 이를 갱신한다. 반면 `resyncFromServer`는 코트·선수·그룹 이력을 복구하면서 `lastGameType`을 패치하지 않는다. `refetchMatches`도 코트만 갱신한다.

**재현 조건:** 기존 직전 유형이 남복인 선수가 혼복을 시작하고 끝내는 동안 한 기기가 연결을 잃어 두 이벤트를 모두 놓친다. 해당 기기가 일반 resync로 돌아와도 그 선수의 직전 유형은 남복으로 남는다. 전체 초기 로드를 하는 다른 기기에는 혼복으로 구성될 수 있다.

**영향:** 같은 선수·코트·그룹 이력을 보더라도 기기마다 로테이션 비용이 달라질 수 있다. 회원 파티 역시 클라이언트에서 점수를 계산하므로 이 차이를 물려받는다.

**제안:** 초기 로드와 복구가 공유하는 직전 유형 파생 함수를 만들고 완료·진행 중 경기로 복구한다. 조회 중 도착한 최신 이벤트를 과거 스냅샷이 덮지 않도록 버전·시각 정책도 함께 적용한다.

근거: [초기 로드](../src/lib/supabase/transformers.ts) `snapshotToClientState`, [이벤트 갱신](../src/store/sessionBroadcastHandlers.ts), [복구 경로](../src/store/sessionStore.ts) `resyncFromServer`·`refetchMatches`, [완료 경기 조회](../src/lib/supabase/board.ts) `dbLoadCompletedMatchTeams`.

### R4. 경기수 우선과 재결성 금지를 절대 규칙으로 설명할 수 없음

**기존 표현:** ‘경기수 > 중복 회피 > 실력’, ‘2인 겹침은 경기수 1판을 못 뒤집는 타이브레이크’, ‘완전 재결성 사실상 금지’.

**실제:** 모든 항목을 합산하고 이력·대기 비용은 누적한다. `W_GROUP2=8`이 `W_GAME=10`보다 작은 것은 **과거 경기 1건의 해당 항만 비교할 때**의 관계다.

**실행한 반례:** 선택된 선수 S와 후보 A는 각각 2판, 후보 B는 3판이다. A와 S가 함께 나온 과거 완료 경기가 2건이며, B의 과거 경기는 S와 겹치지 않는다. 판수·이력·새 만남 외 비용은 같고 대기시간은 0이다.

| 후보 | 판수 비용 | 2인 겹침 비용 | 새 만남 | 총비용 | 순위 |
| --- | --- | --- | --- | --- | --- |
| A | 20 | 8 × 2 = 16 | 0 | 36 | 2 |
| B | 30 | 0 | -12 | 18 | 1 |

최초 검증 당시 B는 새 만남 보정 없이 30점이었고, 이후 -12점 보너스가 추가됐다. 판수가 절대 우선이 아니라는 반례는 유지된다.

그 밖에도 실력 확장 3등급의 비용은 13.5로 한 판 비용보다 크다. 대기 비용은 분당 -1이고 상한이 없어 60분을 넘으면 재결성 1건의 +60을 상쇄할 수 있다. 성별 비용 역시 금지 검증이 아니다.

**제안:** 현재 방식을 유지할 때는 ‘판수 형평을 중시하는 합산 비용’이라고 설명한다. 실제로 절대 우선이 필요한 조건은 후보 필터·단계별 선발·비용 상한 중 어떤 방식으로 강제할지 별도 결정한다. 시간 눈금을 경기 순번으로 바꾸는 것만으로 상한이 생기지는 않는다. 경기 순번 차이도 별도 제한이 없으면 계속 커질 수 있다.

근거: [기본 비용](../src/lib/teamSelection/rankCandidates.ts) `computeScore`, [추천 가중치](../src/lib/teamSelection/recommendTeammates.ts) `RECOMMEND_WEIGHTS`. 문서의 절대적인 표현은 이번 정리에서 보정했다.

### R5. 합류 보정의 활성 평균과 적용 시점이 불완전

**기획 취지:** 늦참·휴식 시간이 추천 우선도를 과도하게 높이지 않도록 합류 시점의 평균 판수로 보정한다.

**보완 전:** `_session_avg_game_count`는 같은 세션에서 본인과 `resting`만 제외한 `game_count`를 **반올림 평균**했다. 콕 체크가 켜져 있어도 미확인 대기자가 들어갔고, 체크 OFF에서는 새 선수 추가 시 판수 보정이 없었다.

**수치 예:** 본인 외에 콕 확인한 4명이 각각 4판이고, 아직 콕 미확인한 4명이 각각 0판이면 보완 전 평균은 2판이었다. 보완 후에는 확인된 기존 참가자 평균인 4판을 적용한다.

**적용 기준:** 늦참 시점 평균을 반영하자는 사용자 제안에 따라, 기존 대기/경기 중 참가자의 판수를 기준으로 구현했다. 본인·휴식·ON일 때 미확인은 제외한다. 진행 중인 판은 미리 더하지 않는다. 기존 보정값이 포함된 `game_count`를 계속 사용하므로 실제 출전 횟수와는 다르며, 출전 순서 자체를 보장하는 모델은 아니다.

**보완:** ON에서는 최초 콕 확인, OFF에서는 신규 INSERT 시점에 `max(기존 판수, 반올림 평균)`을 적용하고 대기시간을 시작한다. ON → OFF에서는 전환 전 확인된 참가자의 평균으로 미확인 대기자를 보정한다. 중복 확인·기존 선수 upsert·중복 추가·OFF 재저장에는 재보정하지 않는다. 휴식 복귀도 보완한 평균 함수를 사용한다.

**검증:** `node --test supabase/tests/late_join_game_count.test.mjs` — 11개 통과. 실제 보완 SQL과 기존 휴식 복귀·자식 변경 동기화 함수를 PGlite에서 실행했다. 대상 필터·반올림·등록/확인 시점·ON/OFF·동시 여러 명 추가·기존 판수 보존·재확인·upsert·설정 전환·휴식 복귀·실행 권한을 검사했다. 단일 로컬 연결 검증으로 기기 간 동시 요청이나 운영 DB 배포를 검증하지는 않았다.

관련 기존 회귀 검사도 `pnpm exec vitest run src/lib/teamSelection src/lib/board/recommendPool.test.ts src/lib/supabase/sessionSync.test.ts src/lib/supabase/sessionSettings.test.ts --reporter=dot`으로 실행해 5개 파일·52개 검사가 통과했다.

**추가 수학 검증:** [증명과 실행 결과](TEAM_MATCHING_MATH.md)에서 평균 오차 0.5판, 반복 합류 시 반올림 기준 유지·분산 비증가를 확인했다. 5,004개 판수 조합 및 늦참 인원 1~20명 조합을 검사했다. 동시에 완료 직전/직후의 최대 1판 차이와 그룹 이력 때문에 늦참자가 먼저 추천되는 반례를 확인했다. 따라서 R5의 구현 누락 보완을 출전 기회의 완전한 공정성 보장으로 해석하지 않는다.

근거: [보완 SQL](../supabase/migrations/20260907040000_late_join_game_count.sql), [SQL 회귀 검사](../supabase/tests/late_join_game_count.test.mjs), [기존 휴식 복귀 SQL](../supabase/migrations/20260817020000_advisor_function_search_path.sql) `set_player_resting`, [추가 선수 생성](../src/lib/supabase/sessionSync.ts), [추천 자격](../src/lib/board/recommendPool.ts). **운영 DB 적용 전.**

### R6. 허용 설정과 실제 성별 분류의 의미가 어긋남

**기획 표현:** ‘남복 편성 허용 여성’은 남3·여1 구성을 허용할 사람을 지정하는 설정처럼 읽힌다.

**실제:** 허용되지 않은 남3·여1도 금지하지 않고 `남복`으로 반환한다. 남1·여3도 `남복`이다. 추천은 남녀가 섞이면 혼성 목표로 비용을 계산하지만, 최종 분류가 남복이면 이후 로테이션에서 동성 이력으로 해석한다. 허용된 여성의 남3·여1만 `혼합`으로 기록된다.

**실행 확인:** `determineGameType`에 미허용 남3·여1과 남1·여3을 각각 넣었으며 둘 다 `남복`을 반환했다.

**영향:** 설정명이 약속하는 허용 범위와 실제 동작이 다르다. 분류 문제는 표시뿐 아니라 다음 경기의 로테이션에 연결된다.

**제안:** 성별 구성을 제한하려면 미허용 조합을 선발 완료·수동 확정·서버 배정에서 검증한다. 제한 없이 허용한다면 남3·여1과 남1·여3의 유형을 일관되게 정하고 설정명을 실제 효과에 맞춘다. 어느 정책을 택할지는 이번 검토에서 확정하지 않았다.

근거: [유형 분류](../src/lib/teamSelection/pairPlayers.ts) `determineGameType`, [추천 혼성 판정·허용 예외](../src/lib/teamSelection/recommendTeammates.ts) `targetMixed`·`genderImbalance`, [설정 UI](../src/components/setup/SingleWomanSelector.tsx).

### R7. 추천 화면과 자동편성의 점수 정책이 다름

**기획 표현:** 자동편성은 ‘추천도 높은순’으로 채운다. 상세 문서에는 경기 중 후보 비용이 고정된 것처럼 설명되어 있었다.

**실제:** `useTeammateRecommendations`는 대기 후보 중 상대 적합도 10% 이상이 없으면 `W_PLAYING=0`으로 다시 계산한다. `autoFillTarget`은 이 예외를 거치지 않고 기본 `W_PLAYING=30`을 사용한다. 자동편성의 팀당 예약 1명 제한은 제거했으며, 새 팀의 대기 anchor 한 자리는 확보한다.

**실행 예:** 같은 실력·이력, 대기시간 0인 후보가 경기 중 0판 선수와 대기 중 4판 선수뿐이면 기본 비용은 30과 40이다. 대기자의 상대 적합도가 0%여서 모달은 0과 40으로 재계산하지만 자동편성은 30과 40을 사용한다. 이 예에서는 순위가 같아도 점수 정책이 다르다는 사실을 보여준다. 이후에도 선택된 구성에 따른 재계산과 새 팀의 대기 anchor 확보 때문에 화면 순위를 그대로 채우는 결과를 보장하지 않는다.

**제안:** 두 경로를 같게 할 것인지, 수동 선택만 더 넓은 참고 목록을 보여줄 것인지 정한다. 현재 예외와 자동편성의 대기 anchor 조건은 이번 기획·알고리즘 문서에 명시했다. 적합도 %를 성공 확률로 설명하지 않는다.

근거: [모달 추천 훅](../src/hooks/useTeammateRecommendations.ts) `deprioritizePlaying`, [자동편성 액션](../src/store/board/membershipSlice.ts) `autoFillTarget`, [선발 반복](../src/lib/teamSelection/recommendTeammates.ts) `autoFillTeammates`.

### R8. 미등급 선수의 의미가 단계마다 다름

**기획 기준:** 판독 불가 등급 0은 정보 없음이며 실력 최하위가 아니다.

**실제:** 선발 함수는 등급 0인 후보에게 실력 비용을 주지 않고, 선택된 0등급 선수도 실력 범위 계산에서 제외한다. 페어 함수는 `skillScore`의 0을 그대로 합·차 계산에 사용한다.

**실행 확인:** 5등급 시드에 미등급 후보를 넣으면 선발의 실력 비용은 0이다. 미등급 1명과 5등급 3명의 페어 비용은 10이다(`intraDiff=5`, `interDiff=5`). 5등급 4명의 비용 0과 다르게 평가된다.

**영향:** 선발에서는 정보가 없는 사람을 페어 편성에서는 강한 선수와 짝지어 균형을 맞출 대상으로 볼 수 있다. 실제로 미등급 선수가 얼마나 있는지는 이번에 조사하지 않았다.

**제안:** 미등급의 임시 등급을 사용할지, 해당 페어 비용을 부분 평가할지, 편성 전 등급 입력을 요구할지 정하고 두 단계에 같은 정책을 적용한다.

근거: [등급 판독·선발 비용](../src/lib/teamSelection/rankCandidates.ts) `skillScoreOf`·`computeScore`, [페어 비용](../src/lib/teamSelection/pairPlayers.ts) `pairingScore`.

### R9. 추천 디버그 표의 표시 항목 합과 총점이 다름

**기획 기준:** 디버그 분해표에서 후보의 추천 비용을 항목별로 설명한다.

**수정 전:** 계산 결과의 `wait`·`mixed`를 표가 렌더하지 않았다. `W_WAIT=1`이므로 대기 중인 후보의 표시 항목 합과 총점이 달랐다.

**예:** 나머지 비용이 20이고 15분 대기했다면 총점은 5지만 표의 항목 합은 20으로 보였다.

**수정:** 새 만남 보정 추가와 함께 `새 만남`·`대기`·`혼복수` 열을 넣어 9개 점수 항목을 모두 표시한다. 각 열의 소수점 표시 반올림 차이는 있을 수 있다. 합계 회귀 검사는 새 만남 항까지 포함하며 앱 배포 전이다.

근거: [비용 구성](../src/lib/teamSelection/rankCandidates.ts) `ScoreBreakdown`, [추천 모달 표](../src/components/board/RecommendTeammateDialog.tsx) `fmtScore`를 사용하는 렌더 열.

### R10. 같은 4명의 페어 변경이 저장되지 않음

**실제:** 경기 수정 모달은 슬롯별 차이로 변경 여부를 판단하지만 `handleSetMatchRoster`는 원래 선수 중 빠진 사람이 없으면 `removed.length === 0`에서 반환한다. 같은 4명의 A/B 배치만 바꾸면 화면에서는 수정 가능하지만 서버 요청은 없다.

**재현 절차:** A편 `[A, B]`, B편 `[C, D]`, 벤치 E인 경기에서 모달 안에서 A→E, C→A, E→C 순서로 교체한다. 최종 배치는 `[C, B]`와 `[A, D]`로 바뀐다. ‘수정하기’를 눌러도 선수 집합은 같아 조기 반환된다.

**영향:** 운영진이 경기 중 두 편을 바로잡으려 해도 변경이 사라진다. 이 판단은 정적 경로 확인이며 브라우저 조작 재현은 수행하지 않았다.

**제안:** 변경 없음의 기준을 선수 집합이 아니라 최종 `teamA/teamB` 배치로 판단하고, 교체 인원이 없는 페어 변경도 저장한다. 같은 편 안의 순서만 바뀌는 경우를 의미 있는 변경으로 볼지도 정한다.

근거: [모달의 `changed`·`swap`](../src/components/board/MatchEditModal.tsx), [store의 조기 반환](../src/store/sessionStore.ts) `handleSetMatchRoster`.

## 4. 모순으로 단정하지 않은 동작

- **확정 순번을 건너뛰어 시작:** 보드 기획에 안내만 하고 강제하지 않는다고 명시되어 있고 코드도 일치한다. 엄격한 선착순이 필요하면 신규 정책 변경이다.
- **진행 중 경기의 조합을 재결성 이력에서 제외:** 완료 시 누적한다는 현재 정의와 일치한다. 예약 선수의 직전 동반자를 미리 회피하려면 이력 범위 변경이 필요하다.
- **회원 파티에서 구한 페어를 경기 시작 시 재계산:** 파티는 4인 확정 팀을 생성한다. 최종 페어 고정 기능으로 보려면 별도 저장·시작 정책이 필요하다.
- **그룹 이력에 최근성·같은 편 구분 없음:** 현재 데이터 모델과 의도에 맞는 제약이다. 랜덤 동점 페어 선택만으로 동반 다양성이 보장되지는 않는다.
- **운영진의 여러 명 예약:** 자동편성의 팀당 예약 1명 제한은 제거했다. 자동·수동 모두 여러 명을 예약할 수 있지만, 자동편성은 다른 팀에 이미 예약된 선수를 제외한다. 회원 파티의 대기 선수 전용 규칙은 별도다.


검사 파일은 [team-matching-repro.test.tsx](../scripts/team-matching-repro.test.tsx)다. 현재 결과는 **대조군 2개 통과 / 문제 재현 검사 8개 실패**, 종료 코드는 1이다. 실패를 통과로 처리하는 `it.fails`를 쓰지 않았으며, 일관된 동작을 기대하는 assertion이 실제로 실패하도록 두었다. 별도 설정으로 실행하므로 기본 `pnpm test`에는 포함되지 않는다.

| --- | --- | --- | --- |
| R1 화면, 2건 | 휴식 선수와 콕 미확인 선수가 있는 경기 수정 모달 렌더 | 일반 추천처럼 후보에서 제외 | 둘 다 교체 목록에 표시 |
| R1 반영, 2건 | 위 선수를 넣는 `handleSetMatchRoster` 호출 → 실제 DB 호출 함수 → 로컬 SQL | 원래 참가자를 유지하고 편입 차단 | 두 경우 모두 경기 참가자로 저장 |
| R2 유형 | 혼복의 여성 1명을 남성으로 교체. 남은 여성은 남복 편성 허용 | `determineGameType`과 DB 모두 혼합 | 유형 함수는 혼합, DB는 혼복 |
| R2 직전 유형 | 직전 남복인 남성 선수를 진행 중 경기에 편입 | 현재 경기 유형을 로테이션 이력에 반영 | 직전 유형은 남복으로 남음 |
| R2 완료 집계 | 위 남3·여1 경기를 완료 | 혼복이 아니므로 새 참가자의 혼복 수 증가 없음 | 혼복 수 0→1 |
| R3 복구 | 시작·완료 이벤트를 생략하고 최신 서버 상태로 resync | 초기 로드와 동일하게 직전 유형 혼복 | 코트·그룹 이력은 복구, 직전 유형은 남복 유지 |

대조군은 일반 추천의 제외 규칙과 가용한 선수의 정상 교체를 확인한다. 따라서 DB 준비나 store 실행 자체가 실패해서 문제 검사가 실패한 것은 아니다. R3도 서버 버전·코트·그룹 이력이 실제 반영됐음을 먼저 확인한 뒤 직전 유형을 비교한다.

**검증 경계:** 운영 데이터 없이 가상 선수 7명을 만들고 메모리 PGlite에서 저장소의 `set_match_roster`·`complete_match` SQL 본문을 실행한다. 네트워크 전송은 로컬 SQL 호출로 대체하고, 권한 검증은 이미 편집권을 가진 운영진이라는 전제로 통과시킨다. 최소 테이블 구조를 사용하므로 운영 전체 스키마·RLS·권한 경쟁을 검증한 결과는 아니다. UI는 실제 모달의 후보 계산을 렌더하되 포털·사진·React 구독 경계만 검사용으로 대체한다. 실제 브라우저 클릭이나 연결 장애를 만든 것은 아니다.

**해석:** R1은 ‘경기 수정도 일반 편성과 같은 참여 조건을 따른다’는 기준의 검사다. 운영진의 강제 편입이 의도라면 그 예외를 먼저 기획에 명시하고 기대값을 조정해야 한다. R2는 최종 로스터 기준 유형·집계, R3은 초기 로드와 재연결의 이력 일치를 기준으로 한다.

화면까지 확인하려면 운영 세션과 분리된 테스트 환경에서 다음 순서로 재현한다.

1. 콕 체크를 켜고 가용 선수·휴식 선수·미확인 선수를 준비한다. 일반 추천 목록과 경기 수정 목록에 같은 이름이 나오는지 비교하고, 교체 후 상태·콕 확인 값도 확인한다.
2. 남2·여2 혼복을 시작한 뒤 여성 1명을 남성으로 교체한다. 남은 여성은 남복 편성 허용 상태로 둔다. 저장된 `matches.game_type`, 새 참가자의 `lastGameType`, 완료 후 `mixed_count`를 비교한다.
3. 두 브라우저 중 한쪽을 오프라인으로 전환한 동안 다른 쪽에서 경기를 시작·완료한다. 첫 브라우저는 새로고침 없이 재연결하고, 다른 브라우저는 초기 로드한다. 같은 선수에 대한 `lastGameType` 또는 같은 선택 멤버·후보의 추천 디버그 ‘로테’ 비용을 비교한다. 대기시간이 포함된 총점보다 로테이션 항목을 비교해야 시각 차이를 배제할 수 있다.

## 6. 결정·수정 순서 제안

1. **경기 수정의 계약:** 참가 자격 예외 여부를 정하고 R1·R2·R10을 함께 수정한다. 최종 로스터·유형·선수 상태를 일관되게 저장한다.
2. **추천 이력 복구:** R3을 수정하고, 연결을 잃었다가 돌아온 기기와 초기 로드 기기가 같은 직전 유형을 갖는지 검증한다.
3. **정책 문구와 실제 강제 조건:** R4·R6에 대해 현재 합산 방식 유지 여부, 성별 조합 허용 범위를 정한다. R5의 평균 보정은 로컬 구현·검증을 마쳤으며 운영 DB 반영이 남았다.
4. **추천 설명의 일관성:** R7·R8의 화면 예외·미등급을 맞춘다. R9 분해표는 새 만남 보정과 함께 수정했고 앱 배포가 남았다.

새 기획에는 로컬 구현 기준 동작을 기록했고, 미해결 항목은 이 검토의 ID로 연결했다. R5의 보완 내용과 운영 DB 미적용 상태는 별도로 표시했다.

## 정리 방향

운영진은 **누가 무엇을 내야 하는지**, **누가 실제로 얼마를 보냈는지**, **남은 금액을 어느 달에 정산할지**를 확인할 수 있어야 한다. 부과 취소·발행, 납부, 환불, 이월이 한 흐름으로 이어진다.

현재 혼란은 다음 세 가지가 겹친 결과다.

1. 발행 후 변경 정책이 서로 다르다. 대관 총액 수정은 전부 초기화, 수동 부과 수정은 납부분 고정, 회원 비활성화는 과거 미납 삭제다.
2. 현재 ‘이월’은 미납만 넘기고, ‘이월 정산’은 면제로 처리한다. 앞으로는 **미납과 남은 입금을 모두 다음 정산으로 넘기는 기능**이 되어야 한다.
3. 화면마다 계산과 조회 범위가 다르다. 월별 원입금 후보, 카드와 상세의 미납 계산, 운영진과 회원 장부가 서로 어긋난다.

따라서 시간 표시·다른 달 검색 같은 화면 개선과 함께 **취소 후 발행, 회원별 이월, 회원 식별, 공통 집계**를 기준으로 기획을 정리한다. 수입·지출은 계속 실제 통장 거래만으로 기록한다.

## 용어와 화면 책임

| 표현 | 사용자에게 약속하는 동작 |
| --- | --- |
| 부과 발행 | 대상 회원·항목·금액을 확정해 낼 돈으로 공개 |
| 부과 취소 | 기존 낼 의무를 취소. 그 부과에 사용했던 입금은 다시 사용할 수 있는 잔액이 됨 |
| 취소 후 발행 | 기존 부과를 취소하고 새 명단·금액으로 발행. 두 부과의 관계와 납부금의 이동을 함께 기록 |
| 납부 확인 | 실제 입금을 부과에 사용. 입금 없이 완납으로 만들지 않음 |
| 납부 연결 해제 | 잘못 사용한 배분만 되돌림. 입금 자체는 남음 |
| 이월 | 선택한 미납과 남은 입금을 지정한 달의 회원 정산으로 넘김. 입력·확인·내역은 하나의 기능 |
| 환불 대기 | 회원에게 돌려줄 것으로 정했지만 아직 출금되지 않은 돈 |
| 환불 완료 | 실제 출금이 원입금 잔액에 연결된 상태 |
| 이월 내역 | 넘어온 미납, 넘어온 입금 잔액, 사용한 금액, 아직 남은 금액을 함께 표시 |
| 모금/직접 수입 | 회원의 낼 의무 없이 묶음에 귀속한 클럽 수입 |

화면은 현재 4개 탭을 유지하는 안을 우선한다. **현황**은 부과·미납·이월을 찾는 곳, **정산함**은 통장 거래와 잔액의 용도를 정하는 곳, **회계**는 월 통장 장부, **부과**는 발행·취소·새 발행 이력을 관리하는 곳이다. 한 묶음/회원/거래를 클릭하면 이 화면들이 같은 ID를 따라 연결되어야 한다.

현황은 **조회와 상태 확인에 집중**한다. 상단은 선택 월 회비의 납부 인원·금액·진행률, 아래는 대관/모임별 납부 상태, 해당 월까지 납기가 도래한 회원별 미납, 이후 납기로 넘긴 미납과 보관 중인 이월 입금이다. 명단과 미납 근거는 화면 안에서 펼쳐 읽는다. 납기 이월은 완납으로 세지 않으며, 회원의 현재 활성 여부로 이미 발행된 부과를 숨기지 않는다. 부과액/납부액은 선택 월에 발생한 유효 부과 기준이므로, 이전 달 원입금으로 납부한 금액도 포함한다. 취소·면제된 부과는 납부 인원과 진행률에서 제외한다.

현황의 변경 작업 버튼·선택 체크박스·작업 이력·복구 도구는 제거한다. 통합 이월과 이월금 적용은 부과 탭에서, 통장 정산은 정산함에서 처리한다. **회계 변경 이력과 부과 운영·복구는 회계 탭 하단**에 모으며, 이력은 선택 월과 무관한 최근 작업이라는 조회 범위를 표시한다.

정산함의 일상 처리는 **목록에서 선택 → 같은 카드의 확인 한 번**으로 끝낸다. 납부자·미납 항목·지출 항목·환불 원입금·이월 월을 카드 안에서 선택하며, 선택 중 서버 미리보기를 자동 실행해 금액과 잔액을 확인 버튼 위에 표시한다. 별도의 미리보기 버튼이나 확인 모달을 요구하지 않는다. 미매칭 입금은 납부자 지정과 납부/이월을 한 명령으로 저장하고, 둘을 함께 되돌릴 수 있어야 한다. 동명이인은 직접 선택하며, 대납은 보낸 사람과 낼 사람을 구분하고 별도 동의를 받는다.

기존 이름 매칭으로 납부자가 지정됐더라도 **아직 전액이 미정산 잔액인 입금**은 납부 연결에서 실제 납부자를 다시 선택할 수 있다. 동명이인은 기존 값을 자동 선택하지 않고 생년·회원 구분과 입금 월 회비의 완납/미납을 함께 보여준다. 납부자를 바꾸면 선택한 부과를 지우고 새 납부자의 미납을 표시한다. 변경 전후 납부자를 확인한 뒤 ‘납부 확인’ 한 번으로 입금 전체의 납부자 변경과 납부를 함께 기록하며, 되돌릴 때도 둘을 함께 복원한다. 일부라도 납부·환불에 사용한 이력이 있는 입금(납부 연결 해제 이력 포함), 이월·환불 대기·클럽 귀속 잔액은 이 변경 대상이 아니다. 다른 사람의 부과를 대신 내는 대납과 납부자 재선택은 별개다.

일상 정산의 처리 사유는 거래와 작업 종류로 자동 기록하고, 추가 설명은 ‘메모 추가’에서 입력한다. 정산함은 미귀속·회원 잔액·환불 대기와 미분류 출금만 보여준다. 전체 보기 전환은 두지 않는다. 처리 후 남은 금액이 있으면 계속 표시하며, 분류/납부/이월/환불이 끝난 거래는 정산함에서 빠진다. 미리보기 이후 다른 처리가 반영되면 갱신된 결과를 다시 확인해야 한다. 저장 응답을 받지 못한 경우에는 같은 요청으로 결과를 조회해 중복 정산하지 않는다.


회계 페이지 하단에는 선택 월의 **전체 거래 내역**을 최신순으로 표시한다. 기존 장부의 간략한 두 줄 목록을 따른다. 날짜·적요·입출금액, 처리 내역·원본 통장 잔액을 보여주고 이름/처리 내역 검색과 항목 필터를 제공한다. 거래를 펼치면 현재 연결을 확인하거나 변경·해제할 수 있다. 연결 해제로 미정산 금액이 생기면 다시 정산함에 표시한다. 저장된 지출 항목은 처리 완료로 표시하고, 변경 화면에서도 처음부터 선택되어 있어야 한다. 기존 항목을 다시 고르거나 그대로 닫는 동작은 저장하지 않으며, 실제로 변경했을 때만 저장 버튼을 제공한다.

미납 목록·입금 잔액·부과 취소 결과에서 누르는 **[이월]은 같은 회원별 이월 화면**을 연다. 서로 다른 메뉴로 ‘납기 연기’와 ‘돈 보관’을 만들지 않는다.

회원 화면은 **이번 달 낼 돈과 계산 근거 / 다음 달 이월 / 환불 대기 / 사용·환불 이력**을 보여준다. 이월 내역 안에서 ‘추가로 낼 돈’과 ‘이미 낸 돈’을 풀어서 표시한다. 합계만 보여 원래 어떤 부과·입금에서 왔는지 감추지 않는다.

## 부과 변경: 취소 후 발행

**확정 방향:** 발행한 부과의 명단·금액을 고치는 기능은 없앤다. 바뀔 대상의 부과를 취소하고 새 부과를 발행한다. 발행 전 초안은 편집할 수 있다.

**권장 상세 흐름:**

1. 취소할 부과를 선택한다. 회원 한 명 또는 묶음의 여러 명을 선택할 수 있다.
2. 취소만 할지, 취소 후 새로 발행할지 고른다. 새로 발행하면 기존 명단·금액을 작성 재료로 가져와 필요한 값을 바꾼다.
3. 기존 납부금이 있으면 **어느 원입금에서 얼마가 풀리는지**, 새 부과에 얼마를 사용할지, 남는 돈 또는 추가 미납이 얼마인지 확인한다.
4. 확정하면 기존 부과는 취소 기록으로 남고 새 부과가 별도로 생긴다. 새 부과에는 앞서 취소한 부과와의 연결이 남는다. 이미 취소/면제된 사람은 자동으로 새 명단에 넣지 않는다.
5. 기존 납부금을 새 부과에 사용하고 남은 돈은 [환불] 또는 [이월]로 처리한다. 돈이 부족하면 새 부과의 차액이 미납이다. 기존 입금이 여러 사람에게 배분돼 있으면 납부자별 원금 한도와 귀속을 보존한다.

취소·새 발행·확인한 입금 사용은 한 번에 반영한다. 중간에 새 부과만 미납으로 보이거나 같은 입금이 두 부과에 동시에 사용된 상태를 만들지 않는다. 취소만 하는 경우에도 원부과에 쓰였던 금액만 풀며, 같은 입금으로 낸 다른 부과의 연결은 유지한다.

| 기존 부과와 납부 | 취소 후 새 발행 | 결과 |
| --- | --- | --- |
| 30,000원 부과 / 미납 | 24,000원 발행 | 새 미납 24,000원. 이월할 입금 잔액은 생기지 않음 |
| 30,000원 부과 / 10,000원 납부 | 24,000원 발행 | 기존 입금 10,000원을 사용하면 새 미납 14,000원 |
| 30,000원 부과 / 30,000원 납부 | 24,000원 발행 | 기존 입금 24,000원을 사용하면 잔액 6,000원 → 환불 또는 이월 |
| 30,000원 부과 / 30,000원 납부 | 34,000원 발행 | 기존 입금 30,000원을 사용하면 추가 미납 4,000원 |
| 30,000원 부과 / 30,000원 납부 | 취소만 | 입금 잔액 30,000원 → 환불 또는 이월 |

취소는 환불 송금이 아니다. 취소 기록과 실제 입금은 남는다. 새 발행이 실패하면 기존 부과·납부가 유지되어야 한다. 취소한 부과를 규칙 재실행이 새 부과와 별도로 되살려서도 안 된다.

한 입금에 회원 납부와 클럽 직접 수입이 섞여 있으면, 취소로 풀린 납부금은 **원래 돈 소유자의 잔액**으로 돌아간다. 기존 클럽 귀속액은 그대로다. 예: 54,000원 중 회식 납부 30,000원·클럽 귀속 24,000원에서 회식만 24,000원으로 취소 후 발행하면, 새 납부 24,000원·클럽 귀속 24,000원·회원 잔액 6,000원이다. 게스트 대납금도 실제 소유자에게 돌아간다.

- 이미 이월한 입금에서도 미사용 금액을 환불할 수 있다. 환불 대기로 돌린 금액은 다음 부과에 사용할 이월 잔액에서 즉시 빠진다. 실제 출금 연결 전까지 ‘환불 완료’로 표시하지 않는다.
- 환불 완료는 통장에서 출금된 뒤의 연결이다. ‘환불 예정’만으로 출금을 만들거나 부과를 paid로 바꾸지 않는다.

- 환불 연결 취소는 출금의 용도 연결만 해제한다. 실제 돈이 돌아온 것으로 처리하지 않는다. 실제 재입금이 있으면 별도 입금 거래다.

### T03. 미납과 남은 돈을 하나로 이월

**확정 방향:** 이월은 ‘이번에 끝내지 않은 회원 정산을 지정한 달로 넘기는 기능’이다. 미납을 다음에 받는 경우와 이미 받은 돈을 다음에 쓰는 경우를 **한 화면·한 이월 내역·한 정산 계산**으로 다룬다.

#### 어떤 금액을 넘기는가

| 이월할 내용 | 대상 월에서의 의미 | 원래 기록 |
| --- | --- | --- |
| 아직 안 낸 부과 잔액 | 다음에 더 내야 할 돈 | 원부과를 유지하고, 선택 금액을 대상 월에 낼 돈으로 이동 |
| 초과 입금·부과 취소 후 남은 입금 | 다음에 낼 돈에서 차감할 돈 | 원입금을 유지하고, 선택 금액을 대상 월부터 사용할 수 있게 지정 |
| 두 종류가 모두 있음 | 더 낼 돈과 이미 낸 돈을 함께 계산 | 원부과·원입금은 각각 남고, 실제 사용 시 서로 연결 |

회비·대관비·수동 부과 모두 같은 이월 기능을 사용한다. 미납 5,000원을 옮겼다고 새 5,000원 부과를 만들지 않고, 입금 잔액 6,000원을 옮겼다고 미래 부과나 새 입금을 만들지 않는다. 새 부과 발행은 **금액·대상을 바꾸는 취소 후 발행**에서만 필요하며, 이월 자체는 부과 내용을 바꾸지 않는다.

**표시 예:** ‘9월 이월: 더 낼 돈 5,000원 · 이미 낸 돈 6,000원 → 정산 후 1,000원 남음’. 합계의 부호만 보여주지 않는다. 원부과가 취소됐거나 원입금이 이미 환불/사용됐다면 그 금액을 이월 후보에 다시 포함하지 않는다.

#### 운영진이 이월하는 흐름

1. 회원의 미납 목록, 남은 입금, 취소 후 발행 결과에서 **[이월]**을 누른다. 모두 같은 화면을 열고 해당 원부과/원입금을 미리 선택한다.
2. **이월할 월**과 **원내역별 금액**을 고른다. 기본 월은 다음 달이며, 더 뒤의 월도 선택할 수 있다. 지금이 9월이면 8월 원입금 잔액을 현재 9월 정산에 넣을 수도 있다. 미래 납기로 미뤄진 미납은 그 납기보다 뒤의 월로 넘긴다. 납기를 앞당기는 것은 이월 취소/월 변경에서 명시적으로 처리한다.
3. 한 화면에서 그 회원의 미납과 확인된 입금 잔액을 함께 볼 수 있다. 각각 전액 또는 일부를 선택한다. 선택하지 않은 미납은 원래 납기에 남고, 선택하지 않은 입금 잔액은 처리 대기/환불 대기 등 기존 상태를 유지한다.
4. ‘넘어갈 미납 / 넘어갈 입금 / 대상 월에 이미 발행된 부과 / 적용 후 예상 납부액 또는 잔액’을 확인하고 확정한다. **아직 발행되지 않은 다음 달 회비는 예상 금액으로 끼워 넣지 않는다.**
5. 원내역에는 ‘9월로 이월한 5,000원’을, 대상 월에는 ‘8월 회비에서 넘어온 5,000원’을 표시한다. 같은 금액을 두 달의 받을 돈에 중복 합산하지 않는다. 이월했다고 납부·면제로 표시하지 않는다.

미납을 일부만 넘길 때도 부과는 하나다. 예: 8월 회식 미납 30,000원 중 10,000원만 9월로 넘기면 8월 납기분 20,000원과 9월 납기분 10,000원으로 설명한다. 20,000원을 먼저 받으면 원부과는 부분납이고 9월의 10,000원만 남는다. 이월 전후 어느 달 화면에서 받아도 **실제 배분된 금액만큼** 남은 납기분이 줄어야 한다.

#### 대상 월에 어떻게 적용하는가 — 권장 상세안

**대상 월이 되었고 사용할 실제 부과가 있으면, 이월한 입금을 그 회원의 낼 돈에 자동 적용하는 안을 권장한다.** 이월 시점의 동의가 ‘그 달부터 다음 납부에 쓴다’는 의미이므로, 매번 [보관금 사용]을 따로 눌러야 하는 흐름을 없앤다. 자동 적용 여부와 아래 순서는 아직 검토할 세부 정책이다.

- 대상 월이 아직 오지 않았으면 미납과 입금 모두 ‘다음 달 이월’로만 표시한다. 그 전 달의 다른 미납에 이월금을 임의로 쓰지 않는다.
- 대상 월에 기존 부과가 있으면 적용하고, 없으면 입금 잔액으로 기다린다. 그 달 중 부과가 새로 발행되거나 이월 미납이 들어오면 다시 적용한다. 화면 조회가 납부를 확정하는 계기가 되지 않도록 발행/이월/월 전환 처리에서 반영한다.
- 대상은 **그 회원 본인의, 현재 납기가 도래한 유효 부과 잔액**이다. 납기순, 같으면 원부과 발생순으로 먼저 사용한다. 이미 이전 달에서 넘어온 미납도 포함한다. 회비·대관·수동이라는 종류로 사용을 제한하지 않는다.
- 남은 입금은 원입금 날짜순으로 사용한다. 실제 돈을 보낸 회원의 잔액과 다른 사람의 부과를 자동으로 섞지 않는다. 게스트 등 다른 사람 대납에 쓰려면 운영진이 회원 요청에 따라 대상과 금액을 명시한다. 부과 대상 회원은 그대로 유지한다.
- 적용 결과는 실제 원입금→부과 납부 연결로 남는다. 부과의 완납/부분납, 이월 내역, 회원의 낼 돈을 동시에 갱신한다. **자동 적용 전 계산 안내와 적용 후 미납을 중복 차감하지 않는다.**
- 입금이 부족하면 차액만 미납이다. 입금이 더 많으면 남은 금액을 이후 발행에 계속 사용할 수 있게 유지하고, 다음 달에도 자동으로 이어 보여준다. 미사용 입금에 임의 소멸 기한을 두지 않는다.
- 미납이 남으면 대상 월의 미납/연체로 남는다. 미납을 다시 다음 달로 넘기려면 같은 [이월]로 명시적으로 처리한다. 매달 자동으로 납기를 미뤄 미납이 계속 숨지 않게 한다.

미납과 입금을 함께 이월한 경우에도 **대상 월 전에는 서로 납부 처리하지 않는다.** 대상 월에 둘을 연결했을 때 미납이 해결되고 남은 입금을 계산한다. 그 전에 받거나 환불해야 하면 이월 월/선택을 변경하고 처리한다.

| 잔액 6,000원을 9월로 이월 | 새 부과의 완납은 그대로 | 6,000원, 9월부터 사용 | 없음 |
| 9월이 되고 9월 회비 5,000원 발행 | 이월 입금 5,000원 적용 → 9월 회비 완납 | 1,000원 | 없음 |
| 이후 대관비 6,000원 발행 | 남은 1,000원 적용 → 대관비 미납 5,000원 | 0 | 없음 |
| 회원이 차액 5,000원 입금 | 대관비 나머지 납부 확인 → 완납 | 0 | 실제 입금월 +5,000 |

다른 부과가 생기기 전에 남은 1,000원을 환불해 달라고 하면, 그 1,000원을 환불 대기로 옮기고 실제 출금에 연결한다. 그 금액은 이후 부과에 사용하지 않는다. 9월 회비에 사용한 5,000원은 끝까지 **8월 원입금의 일부**로 추적한다.

#### 미납과 돈을 함께 이월한 사례

| 9월에 넘어온 미납 | 9월부터 사용할 입금 잔액 | 새로 발행된 9월 회비 | 적용 결과 |
| --- | --- | --- | --- |
| 8월 미납 5,000원 | 없음 | 5,000원 | 총 10,000원을 내야 함 |
| 없음 | 8월 입금 잔액 6,000원 | 5,000원 | 회비 완납, 입금 잔액 1,000원 유지 |
| 8월 미납 5,000원 | 8월 입금 잔액 6,000원 | 5,000원 | 이전 미납에 5,000원, 새 회비에 1,000원 사용 → 4,000원만 납부 |
| 8월 미납 5,000원 | 8월 입금 잔액 6,000원 | 아직 없음 | 이전 미납 완납, 남은 1,000원은 새 부과를 기다림 |

회원에게는 ‘이전 미납 5,000 + 이번 달 회비 5,000 − 이월한 입금 사용 6,000 = 이번에 낼 돈 4,000원’처럼 보여준다. 확인할 원내역도 같은 화면에서 펼칠 수 있어야 한다.

#### 취소·변경·예외

- **이월 월 변경/취소:** 아직 정산되지 않은 금액만 대상으로 한다. 미납 이월을 취소하면 해당 잔액이 원래 납기로 돌아가고, 입금 이월을 취소하면 미사용 잔액이 처리 대기로 돌아간다. 실제 돈이 오간 것으로 기록하지 않는다.
- **이미 사용한 금액:** 이월 기록 삭제로 없앨 수 없다. 특정 납부 연결을 해제하면 그 사용액만 원입금의 이월 잔액으로 복원하고 해당 부과는 그만큼 미납으로 돌아간다. 다른 부과에 쓴 돈은 그대로 둔다. 사용 취소·다른 부과 선택·환불 전환은 하나의 처리로 확정해 자동 적용이 즉시 같은 부과에 다시 쓰지 않게 한다.
- **이월한 미납의 부과 취소:** 원부과가 취소되면 그 부과에서 넘어갈 미납도 없어진다. 미납 금액이 회원 입금 잔액으로 바뀌지는 않는다. 새 부과를 발행할 경우 이월 조건을 이어갈지 확인 요약에서 결정한다.
- **이월 입금으로 낸 부과 취소:** 사용했던 돈을 해당 원입금의 이월 잔액으로 되돌린다. 취소 후 발행이면 새 부과에 쓸 금액을 같은 확인에서 보여준다.
- **회원 비활성/탈퇴:** 이월한 입금의 소유자와 사용·환불 이력은 유지한다. 회원 상태 변경을 이유로 돈을 지우거나 클럽 수입으로 바꾸지 않는다. 발행된 미납을 유지할지는 D01 정책을 따른다.
- **소유자를 모르는 입금:** 먼저 실제 납부자를 확인해야 이월할 수 있다. 입금자 이름이 같은 회원에게 추정으로 잔액을 붙이지 않는다.
- **동시 처리:** 이월 사용과 환불이 동시에 요청되어도 같은 원금은 한 번만 사용할 수 있다. 회원 화면은 이월 입금과 환불 대기 양쪽에 같은 금액을 보여주지 않는다.

**완료 조건:** 미납만 / 입금만 / 둘 다 있는 세 경우를 같은 [이월]에서 처리한다. 다음 달 부과가 아직 없어도 받은 돈을 이월할 수 있고, 부과가 생기면 사용한 원입금과 줄어든 미납을 함께 설명한다. 일부 사용·일부 환불·여러 달 잔액 유지·재이월·취소를 거쳐도 원부과와 원입금이 끊기지 않는다. 이월은 납부나 면제로 집계하지 않으며, 실제 사용이 일어난 금액만 납부가 된다. 이월 중인 입금에는 환불 계좌 요청을 동시에 띄우지 않는다.

### T04. 동명이인 김지훈의 회비 처리

**현재 확인한 사실:** 부과·배분은 회원 ID 기준이고, 비게스트 동명이인은 후보에서 모두 보존한다. 다만 첫 이름 후보가 자동 납부자로 선택되고, 이미 납부자가 있으면 검색 결과 선택이 대납 추가가 된다. **신규 회비는 대납 추가된 사람에게 제공되지 않는다.** 동명 게스트 접기와 결과 상한도 있다.

**추가 조사와 수정:** 운영 DB에서 동명 회원·게스트의 ID, 회비 부과, 실제 배분이 별도로 존재하는 것을 확인했다. 과거 클릭 과정은 기록되지 않아 당시 원인을 단정하지 않지만, 기존 코드의 첫 후보 자동 선택 → 검색 결과를 대납으로 추가 → 추가 대상에게 신규 회비 미제공 경로를 확인했다. 새 화면은 납부자 변경과 낼 사람 선택을 분리하고, 이름/초성 검색에서 모든 ID를 보존한다. 한 사람의 완납 후 동명인의 미발행 회비를 별도로 발행·납부하는 전체 경로를 브라우저와 실제 SQL로 검증한다.

**권장 동작:**

- 이름이 같아도 모든 실제 회원을 별개 항목으로 유지한다. 회원끼리 또는 회원과 게스트를 이름만으로 병합하지 않는다.
- 같은 이름의 유효 후보가 둘 이상이면 납부자를 자동 확정 선택하지 않는다. 성별·출생연도·회원/게스트·참고 참석 회차/초대자 등 확보된 구분 정보를 함께 보여준다. 정보가 부족하면 ‘구분 정보 없음’을 표시하고 관련 부과/참석을 확인하게 한다.
- **[납부자 변경]과 [함께 낼 사람 추가]를 별도 동작**으로 둔다. 검색에서 동명인을 찾았다는 이유로 의도하지 않은 대납으로 바뀌면 안 된다.
- 간단한 추천 목록은 줄여도 [전체 결과]에서 필요한 회원 ID를 모두 찾을 수 있어야 한다. 게스트 과거 방문 부과/선납을 이름 접기 때문에 선택할 수 없게 만들지 않는다.
- 확인 요약은 ‘보낸 사람 → 낼 사람 → 부과월/회차 → 금액’을 보여준다. 게스트 대납이면 그 관계를 명시한다.
- 낼 항목이 없으면 ‘이 월 부과 없음 / 이미 납부 / 취소·면제 / 신규 발행 필요’를 구분한다. 다른 사람의 납부 완료를 현재 선택한 사람에게 적용하지 않는다.

**완료 조건:** 회원 A·B가 모두 김지훈이어도 A의 8월 회비를 납부한 뒤 B의 8월 회비를 독립적으로 처리할 수 있다. B의 부과가 아직 없을 때도 납부자를 B로 바꿔 명시적으로 신규 발행할 수 있다. 같은 이름의 게스트가 추가되어도 각자 부과·잔액·납부 이력이 섞이지 않는다.

## 공통 정책: 확정 방향과 검토할 상세안

**D02의 취소 후 발행, D03의 이월 기능 통합, D08의 월 정산 재집계는 이번 논의에서 확정한 방향**이다. 그에 따른 납부금 사용·자동 적용 등의 상세는 위 흐름을 검토하며 정한다. D01 등 나머지는 계속 권장안으로 남긴다.

| 결정 | 상태와 내용 | 바뀌는 현재 동작 |
| --- | --- | --- |
| D01. 비활성/명예 지정의 소급 범위 | **권장안.** 상태 변경은 향후 발행 자격에 반영. 이미 발행한 회비를 면제/취소할 때는 대상 월·사유를 명시하고 기록 보존 | 비활성/명예 지정이 모든 과거 미납 행을 삭제하는 동작. 재활성화 컷오프로 기존 채무가 사라지지 않게 함 |
| D02. 발행 후 변경 | **방향 확정: 취소 후 발행.** 회비·대관·수동 공통. 기존 부과를 덮어쓰지 않고 취소 기록과 새 부과를 연결. 기존 납부금의 새 부과 사용·차액 환불/이월 흐름은 권장 상세안 | 대관 전부 삭제·재발행과 수동 납부분 금액 고정의 비대칭 |
| D03. 이월 | **방향 확정: 미납과 받은 돈을 하나의 기능으로 통합.** 회원·월별 이월 내역과 낼 돈 계산을 공유. 이월만으로 paid/waived 처리하지 않음 | 납기를 미루는 기능만 존재, 이월을 납부로 세는 진행률과 이월분 면제 버튼 |
| D04. 초안 처리 | **권장안.** 발행 직전 대상/금액 재검증. [초안 폐기]는 후보 제거임을 명시하며 영구 제외가 필요하면 사유가 있는 별도 결정 | 오래된 초안 그대로 발행, 폐기 후 재출현을 부과 취소로 오해 |
| D05. 수동 계산 근거 | **권장안.** 원본 총액·올림 단위·대상 명단을 보존. 취소 후 새 발행의 개인별 금액과 합계를 미리 확인하고 최소 단가를 자동 기준으로 쓰지 않음 | 편집 시 올림 단위 초기화, 기존 최소 단가로 신규 사람 추가 |
| D06. 이월 적용 | **권장 상세안.** 대상 월 도래 + 실제 부과 존재 시 본인 낼 돈에 자동 적용. 일부 사용 후 잔액은 이후 납부에 계속 사용. 다른 사람 대납은 명시 선택 | 잔액이 있어도 전체 미납을 다시 요구하고 매번 입금 전체 재처리에 의존 |
| D07. 마감 | **권장안.** 수납 완료·지출 확인·발행/취소 확인 완료를 각각 표시. 이월한 미납은 ‘다음 달로 넘김’으로 구분하고 원묶음을 완납으로 만들지 않음. 지출이 원래 없는 묶음에는 ‘지출 없음’을 명시 | 모든 묶음에 출금 연결 강제, 누락·초안·규칙 차이가 있어도 마감 표시 |
| D08. 월 정산 | **방향 확정.** 현재 연결 상태를 기준으로 해당 월 실제 입출금을 합산. 과거 항목별 분류 변경 허용. D07의 묶음 처리 상태와 별개로 월 잠금·확정 장부 보관 기능은 만들지 않음 | 월 장부 불변성을 위해 취소·이월을 제한할 필요 없음 |

상태 변경일 이전/이후를 판단할 기준도 필요하다. **권장안은 발행 당시 자격·금액의 근거를 보존하고, 과거 월 신규 발행에는 해당 월 근거 또는 운영진의 사유를 요구하는 것**이다. 지금처럼 현재 `is_active`만 읽어 과거 자격 전체를 추정하지 않는다. 정책 적용 이전 부과를 취소/새 발행할 대상은 별도 목록으로 확인한다.

## 계산과 이력의 공통 기준

다음 항목은 세부 테이블을 확정하기 전의 **기능 계약**이다. 새 테이블 이름·마이그레이션 방식은 구현 설계에서 정한다.

- 각 원입금에 대해 `입금액 = 현재 부과 사용액 + 실제 환불액 + 미사용 이월 입금 + 환불 대기액 + 클럽 직접 귀속액 + 아직 용도 미정인 금액`이 성립한다. 취소된 납부 연결은 사용 이력으로만 남고 현재 사용액에서는 빠진다. 하나의 금액은 한 칸에만 속한다.
- `입금 − 배분 − 환불`의 나머지를 전부 회원 잔액으로 보지 않는다. 클럽 직접 귀속과 회원에게 남은 돈을 금액별로 보존한다. 기존 묶음/분류가 중복 지정돼 있어도 같은 돈을 두 번 이관하지 않는다.
- 원부과의 남은 미납은 납기별 잔액의 합이다. 일부를 이월해도 총 미납은 늘거나 줄지 않는다. 실제 납부·부과 취소·면제만 그 의무를 줄인다. **이월한 미납을 위 입금 보존식에 넣지 않는다.** 같은 기능에서 다루어도 아직 받지 않은 돈이 입금으로 바뀌지는 않는다.
- 이월한 입금의 적용 전 정산 예상액은 `현재 납기가 도래한 미납(이월 도착분 포함) − 사용 가능한 이월 입금`이다. 양수면 추가 납부, 음수면 입금 잔액이 남는다. 실제 적용 후에는 줄어든 미납과 줄어든 이월 잔액을 보여주며 같은 사용액을 다시 빼지 않는다.
- 환불 대기/이월 지정·이월금 사용은 현금 이동이 아니다. 실제 통장 수입/지출은 원거래 날짜(KST)를 유지한다. 과거 월 항목을 재조회해 분류가 달라질 수 있는 것과 과거 통장 총액을 바꾸는 것을 구분한다.
- 취소·새 발행·면제·납부 연결 해제·이월 지정·이월금 사용은 각각 기록된다. 취소한 부과는 새 부과와 구분되고, 부과 금액을 고쳐 원래 금액을 잃지 않는다.
- 취소 후 발행/이월 이동에는 대상 ID, 원입금 ID, 원부과·새 부과 ID, 금액, 이월 전후의 월, 사유, 처리자, 처리 시각을 남긴다. 이월은 같은 원내역을 다른 납기/사용 시점으로 옮기는 것이며 복제하지 않는다.
- 잔액을 사용하는 확정은 서버에서 원자적으로 처리하고, 중복 요청/동시 처리에도 총 사용·환불이 원입금 한도를 넘지 않아야 한다. 부과 배분+묶음 귀속도 같은 확정 단위다.
- 부과 대상 인원, 납부 완료 인원, 실제 송금자 수는 다를 수 있다. 기본 진행률은 **부과 대상 ID별 유효 부과**로 계산하고 대납 송금자 수는 별도 정보다. 면제자를 납부자로 세지 않는다.
- 같은 묶음의 카드·상세는 같은 집계값을 사용한다. 세션/수동 묶음 전체 손익은 월 무관 전체 관련 거래·배분으로, 월 회계는 그 달 통장 거래로 계산한다.
- 운영진 장부와 회원 장부는 같은 분류/환불 산식을 사용한다. 묶음에 붙은 입금은 이미 부과에 사용한 금액을 다시 더하지 않는다. 레거시 카테고리는 이관/정리 완료 전까지 명시된 우선순위로만 해석한다.

## 진행 순서와 검증

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 기존 데이터 영향 조사·새 도메인과 이관 설계, T01·자동 적용 등 상세 검토 | 운영 DB 읽기 조사 완료. 완납·기존 미납·월간 연결·잔액 귀속 확인 |
| 2 | 부과·납기·입금 잔액·납부·환불의 공통 모델과 서버 작업 구현, 기존 데이터 이관기 | 기존 발행·납부 결과를 재생성 없이 보존. 원입금별 금액 대조 |
| 3 | D02 취소 후 발행 + T03 이월 통합 + T02 월 무관 환불과 동시성 처리 | 취소→새 발행→이월/환불→다음 납부까지 원자적·반복 안전하게 처리 |
| 4 | T01 회차 구분·T04 납부자 선택, 공통 회원/묶음/월 장부 조회와 UI, D01/D04/D05 정책 연결 | 동일 ID·동일 산식으로 표시. 기존 미납이 드러나는 변화와 새 부과를 구분 |
| 5 | 실제 자료의 복제본에서 이관·통합 검증 후 새 쓰기 경로로 전환 | 7·8월 완료분과 9월 진행분 유지. 옛 RPC·트리거·직접 쓰기의 우회 방지 |

T01의 표시 개선은 독립적으로 진행할 수 있다. 금액을 사용하는 작업은 공통 모델을 기준으로 구현한다. **이미 완납된 부과를 취소하고 더 적은 금액으로 발행한 뒤 차액을 환불하는 T02에는 취소 후 발행과 잔액 처리까지 필요**하다. 다른 달 검색만 고치고 T02 전체를 완료했다고 표시하지 않는다. 실제 전환·복구 순서는 [구현·적용·복구](ACCOUNTING_ROLLOUT.md)를 따른다. 구현 검토의 단계별 구상보다 이 적용 문서가 우선한다.

검증 시나리오는 T01~T04의 완료 조건에 더해 다음을 포함한다.

- 엔빵 운영진 미납, 당일취소 부분납·면제, 부과 누락/발행 대기 상태의 카드와 상세 비교.
- 하나의 입금에 회식 30,000원 + 모금 24,000원 혼합, 다른 달 지출, 묶음/세션에 연결된 입금의 부분 환불. 모든 화면 합계 일치.
- 취소 후 발행 전에 완납/부분납/미납/void가 섞인 묶음. 취소 기록·새 부과·납부금 이동을 확인하고, 기존 취소자는 다시 부과하지 않음. 새 발행 실패 시 기존 상태 유지.
- 미납만 / 입금만 / 두 종류 모두 이월, 일부 금액만 이월, 대상 월 전/도래 후, 다음 달 부과가 아직 없는 경우와 뒤늦게 발행되는 경우.
- 이월 입금 부족/초과, 여러 원입금의 순차 사용, 미납 재이월, 이미 일부 사용한 이월의 취소·환불·월 변경. 입금이 없는 미납 이월은 납부로 세지 않음.
- 비활성·명예 지정과 재활성화 전후의 과거 발행분·입금 잔액, 실제 납부 완료된 이월분, 초안 생성 후 자격 변경.
- 같은 잔액의 자동 사용·환불·중복 확인, 한 입금을 여러 부과에 사용한 뒤 일부 연결만 취소. 대상 월 전의 입금은 조기 사용하지 않고 다른 회원의 부과에도 자동 적용하지 않음.
- 운영진 처리 후 회원의 미납·이월·환불 대기·납부 이력이 함께 갱신되고, 계정 전환 시 다른 회원 값이 남지 않음.

현재 단위 테스트 통과 여부와 이 통합 시나리오의 완료 여부는 별도로 관리한다. 기존 자료 대조와 추가 통합 시나리오는 [구현 검토 §2·§7](ACCOUNTING_IMPLEMENTATION_REVIEW.md)에 있다. 실제 김지훈 거래의 원인 확인과 기존 미납·잔액의 업무상 처리 결정은 별도 항목이다.

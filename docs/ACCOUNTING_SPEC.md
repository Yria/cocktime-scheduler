## 0. 먼저 구분할 개념

현재 기능은 **낼 의무(부과)**, **실제로 들어오고 나간 돈(통장 거래)**, **그 돈을 어디에 사용했는지(배분·귀속)**의 세 축으로 구성된다. 부과가 생겼다고 수입이 생기지는 않으며, 부과를 취소했다고 돈이 환불되지도 않는다.

| 용어 | 의미 | 현재 표현 |
| --- | --- | --- |
| 부과 | 특정 회원이 특정 항목에 낼 돈 | `dues_charges` |
| 발행 대기 | 규칙이 계산했지만 운영진 확인이 필요한 부과 후보 | `dues_charge_drafts`; 회원에게 비공개 |
| 납부 확인 | 실제 입금의 일부/전부를 부과에 사용 | `dues_allocations` |
| 묶음 | 월 회비·대관 회차·회식/공구 등 정산 단위 | `dues_batches` |
| 직접 귀속 | 부과 없이 들어온 돈이나 지출을 항목에 연결 | 거래의 `batch_id` 또는 `session_id` |
| 부과 취소 | 낼 의무를 무효로 표시 | `status='void'`; 기존 배분은 그대로 |
| 면제 | 부과는 남기고 미납 의무를 해제 | `status='waived'`; 기존 배분은 그대로 |
| 납부 연결 취소 | 입금에 붙인 배분을 해제 | 입금 단위 배분 삭제; 통장 거래·부과는 남음 |
| 환불 | 실제 환불 출금을 원입금에 연결 | `refund_of_tx_id`; 송금 기능은 없음 |
| 회비 이월 | 미납 회비의 표시/납기 월을 다음 달로 이동 | `deferred_to`; 이미 받은 돈의 이월 기능은 아님 |
| 돌려받을 돈 | 일부 배분 후 용도 없이 남은 입금 잔액 | 회원 화면의 계산 결과; 독립 예치금 원장은 없음 |

‘미부과’는 부과 행이 없는 경우, ‘미납’은 발행된 부과의 남은 금액이 있는 경우다. ‘정산 완료’는 화면에 따라 뜻이 다르므로, 회원 납부 완료·거래 처리 완료·묶음 마감을 같은 상태로 취급하면 안 된다(§3·§13).

## 1. 도메인과 금액 기준

### 1.1 부과 종류

| 종류 | 부과 단위 / 식별 기준 | 기본 금액 | 대상의 근거 |
| --- | --- | --- | --- |
| 월 회비 `monthly_fee` | 회원 ID + `period_ym` | 설정값, 기본 5,000원 | 활성·비게스트·비명예·비운영진 + 가입/합류 기준 |
| 대관비 `court_fee` | 회원 ID + `session_id` | 정액·총액 분할·무부과 | 참석 상태와 보드 명단의 합집합 |
| 수동 부과 `manual` | 회원 ID + `batch_key` | 운영진이 정한 인당 금액 | 운영진이 확정한 명단 |

모든 부과는 `batch_id`도 갖는다. 기존 세 식별 축과 묶음 ID가 공존한다. **이름은 식별 키가 아니다.** 회원 이름이나 회차 표시 이름이 같아도 ID가 다르면 별개의 부과다.

수동 부과 종류에는 회식·콕 공동구매·유니폼·물품·기타가 있다. 정해진 사람에게 낼 금액을 먼저 정하면 수동 부과이고, 입금한 사람만 구매자로 집계하면 부과 없이 묶음에 직접 귀속한다. 공동구매라는 이름만으로 둘 중 하나가 결정되지는 않는다.

### 1.2 대관비 계산

유효 총액은 `coalesce(sessions.court_fee, recurring_schedules.court_fee)`다. 회차의 값이 우선이고, 회차 값이 NULL이면 반복 규칙을 조회한다. **회차 칸을 비웠다고 반드시 정액이 되는 것은 아니다.**

| 유효 총액 | 모드 | 금액 / 운영진 처리 |
| --- | --- | --- |
| NULL | 정액 | 인당 기본액(기본 6,000원), 운영진 제외 |
| 0 이하 | 무부과 | 새 대관비를 발행하지 않음 |
| 0 초과 | 총액 분할(엔빵) | 총액 ÷ 대상 수를 10원 단위 올림, 운영진 포함 |

분할 금액을 올린 결과가 `[정액 기본액, 정액 기본액 + 200원)`이면 기본액으로 낮춘다. 예: 117,000원 ÷ 19명 → 6,160원 → 6,000원. 기본액보다 작은 금액은 올려 맞추지 않는다. 부과 합계와 실제 코트 지출은 절상·스냅·지원금 때문에 다를 수 있다.

생성기는 음수도 무부과로 읽지만, 회차 총액 변경 RPC는 음수 입력을 거부한다. 무부과로 바뀌어도 **생성기를 다시 실행하는 것만으로 기존 발행분은 없어지지 않는다.** 총액 변경 RPC를 통한 전체 재발행은 별도 동작이다(§4.4).

### 1.3 날짜와 월

| 기준 | 사용하는 날짜 | 의미 |
| --- | --- | --- |
| 회비 귀속 | `period_ym` | 어느 달의 회비인가 |
| 회비 납기/노출 | `deferred_to ?? period_ym` | 언제 낼 돈으로 보여주는가 |
| 대관비 귀속 | 회차의 KST 날짜 | 어느 회차의 돈인가 |
| 수동 부과 귀속 | `charged_on` | 어느 달 부과 목록에 보이는가 |
| 통장 회계 | `bank_transactions.occurred_at`, KST | 실제 돈이 움직인 달 |
| 발행 시각 | 부과의 `created_at` | 언제 부과 행이 만들어졌는가 |

예: 8월 입금으로 9월 부과를 납부 처리하면 9월 부과가 완납되고, 통장 수입은 8월에 남는다. 9월에 환불 출금이 발생하면 지출은 9월이다. 현재 월별 회계는 다시 조회할 때 배분을 계산하므로, 과거 입금의 배분을 바꾸면 **과거 월의 항목 분류**는 바뀔 수 있다. 통장 월 수입·지출 총액은 바뀌지 않는다.

### 1.4 주요 데이터

| 데이터 | 책임 |
| --- | --- |
| `dues_batches` | 종류(`monthly/court/manual`), 고유 키, 이름, 발생일, 원본 총액(`total_amount`) |
| `dues_charges` | 부과 대상 회원, 금액, 배분 합계 캐시, 상태, 대납 힌트, 이월, 당일취소/취소자 정보 |
| `dues_charge_drafts` | 묶음별 미발행 후보, 대기 사유와 계산 근거 |
| `bank_transactions` | 은행 입출금 원본, 배분 처리 상태, 묶음/세션/환불 연결, 납부자 힌트 `paid_by` |
| `dues_allocations` | 원입금·부과·실제 납부자로 선택한 회원·사용 금액의 연결 |
| `dues_settings` | 회비액, 대관 기본액, 가입일 오프셋, 합류 컷오프, 클럽 계좌 |
| `dues_audit_log` / `raw_bank_emails` | 조작 감사 / 수집 원문 |
| `member_honorary` | 명예회원 지정 사유(운영진 전용) |
| `txn_categories` | 이전 분류 체계. DB·관리 UI·일부 조회에 남아 있음 |

모든 **부과**에는 묶음이 있지만, 미처리 **거래**는 어느 묶음에도 속하지 않을 수 있다. `paid_by`, 부과 대상 `member_id`, 배분의 납부자 `member_id`, 게스트 초대자 `payer_hint`는 역할이 다르다.

현황·정산함·회계·부과 탭의 월 선택은 공통이지만, 모든 조회가 그 달로 제한되지는 않는다(§11).

역할 경계 두 개를 화면 구조로 잠근다.

- **현황은 읽기 전용이다.** 조작(체크박스·명령 버튼)을 심지 않고 조회만 한다. 다른
  탭으로 보내는 카운터 링크는 내비게이션이며 쓰기가 아니다. e2e 가 이 탭의
  `checkbox` 0개와 명령 버튼 0개, 조회 중 `dues_v2_command/preview/manage` 0회를
  단정한다 — 편의 기능을 여기에 얹지 말 것.
- **쓰기는 정산함(거래 1건)과 부과 탭(전표 1건)에서만 시작한다.** 부과 탭의 전표는
  인라인이며 모달이 아니다(§3.7).

## 3. 화면별 현재 동작

### 3.1 현황과 정산 대조

- 회비 진행은 해당 월 부과 행으로 계산한다. 원월에서 이월한 건을 ‘납부’ 수에 포함하고, 이월받은 월에는 별도 목록을 표시한다. 실제 입금 여부와 진행률이 다르다.
- 이월 목록의 **[정산]은 `waived`로 변경**한다. 은행 입금 배분이 아니며, 처리 후 ‘정산 · 금액 미기록’으로 보인다. [취소]는 이월 해제다.
- 회차 카드를 열면 인원 대조 → 금액 대조 → 전체 명단을 본다. 명단은 회원 ID별 한 줄이며, 미납·완납·무효·미부과·발행 대기·확인 필요를 구분한다.
- 회차 상세의 대상 계산은 `sessionSettle.ts`가 서버의 정액/분할/무부과·당일취소·보드 합집합을 재현한다. 현재 규칙과 발행 사실이 다른 것은 확인 대상으로 보이지만 자동 수정하지 않는다. 참석 기록 없는 부과는 대조 근거 없음으로 구분한다.
- 진행 중 미발행 대상과 저장된 초안은 발행 대기, 종료 후 행도 초안도 없는 대상은 누락이다. 초안 배너는 월과 무관하게 표시한다(현황의 ‘발행 검토 대기’ 카운트도 월 필터 없이 전체 초안을 센다 — 부과 탭 숫자와 일치한다). 서버가 보류한 사유(`hold_reason`: 금액 범위 초과·인원 급변·신규 대상)를 부과 탭 발행 대기 목록에 함께 표시한다.
- 회차 상세에서 가능한 부과 조작은 **아직 배분이 없는 당일취소 부과의 [부과삭제] 및 그 void의 [되돌리기]**다. 일반 부과·납부된 부과를 모두 취소할 수 있는 UI는 없다.
- 회차 카드의 진행률/마감 계산은 상세와 별도이며, 모드와 관계없이 운영진을 면제·완료로 센다. 따라서 엔빵 운영진 미납·당일취소 부분납 등이 카드에서 빠질 수 있다. 현재 ‘마감’은 대조의 정확성을 보증하지 않는다(§13 A04).

### 3.2 정산함

입금은 납부자 지정 → 기존 미납 선택 또는 부과 즉석 생성 → 확인의 흐름이다. 다른 회원·게스트의 대납도 선택할 수 있다. 기존 미납은 월과 관계없이 조회한다.

- 신규 회비: 납부자 본인의 입금월 회비. 화면에서 게스트는 제외하지만 자동 부과의 활성/명예/가입 기준을 모두 검사하지는 않는다.
- 신규 대관비: 선택 월의 열린 대관 회차 또는 현재 기준 예정(open) 회차 중 해당 회원이 `confirmed/late_pool`이고 부과가 없는 회차. 보드 추가만 된 사람·당일취소자는 이 신규 칩의 참석 조건을 통과하지 못한다.
- 신규 수동 부과: 입금월 또는 직전 월의 기존 수동 묶음에 해당 회원을 추가한다. 새 단가는 기존 void 제외 부과 중 최솟값이다. 혼합 단가의 별도 결정 정책은 없다.
- 직접 귀속: 묶음을 선택하거나 새 묶음을 만들어 남은 입금을 귀속한다. 부과 선택과 함께 고를 수 있으나, 저장은 별도 RPC 호출이다(§13 A07).
- 비회원 대관: 회원 없이 세션에 입금을 직접 연결한다. 현재 UI는 기본 대관비의 배수 금액일 때 후보를 제공한다.
- 출금: 대관 회차 지정 / 묶음 지정 / 환불할 원입금 선택. 환불은 출금 전액을 원입금 한 건에 연결한다.
- 부분 처리 입금은 별도 요약 행이다. 그 행에서 잔액을 추가 배분하는 편집기는 없다. 기존 처리를 취소한 뒤 재처리하는 흐름에 의존한다.
- 환불 후보는 현재 선택 월에 로드한 미처리/부분처리 입금뿐이다. 후보에 표시하는 금액은 **사용 가능 잔액이 아니라 원입금 전액**이다.

### 3.3 운영진 회계

그 달 통장 수입·지출·순액과 거래별 은행 잔액을 표시한다. 항목은 걷은 회비 / 회차 대관비 / 수동 묶음 / 레거시 카테고리 / 환불 / 미분류로 나눈다.

**항목별 수지는 별도 시트가 아니라 거래 내역 안의 필터 줄이다**(2026-09-11). 항목이
한 달에 15개를 넘어 한 줄에 하나씩 놓으면 필터가 목록보다 길어졌다. 상태 필터(전체·
입금·출금·미정산·환불) 아래에 가로로 흐르는 두 줄짜리 칩으로 접고, 칩 안에 수입·지출을
함께 적는다(대조가 본업이라 두 수를 뗄 수 없다. 0 인 쪽은 생략한다 — 표의 `—` 는 열을
맞추기 위한 자리표시이고 칩에는 열이 없다 — 0 인 쪽을 생략하면 칩마다 수입·지출이
자리를 바꿔 앉아 열이 서지 않는다. 칩 폭도 고정한다).
순서는 **종류 묶음 + 날짜순**이다(`sortLedgerBuckets`): 대관비(회차 날짜) → 회비(월) →
수동 묶음(발생일) → 묶음 없는 합성 항목(환불·환불 원입금·미분류·이월 입금 …, 라벨순).
서버는 라벨 문자열순으로만 주므로 종류·발생일 정렬은 클라이언트 몫이다. 금액 순으로
세우면 날짜가 흩어져 특정 회차를 눈으로 좇을 수 없다(가로 스크롤이라 화면 밖 항목은
아예 보이지 않는다). 누르면 목록이 그 항목으로 좁혀지고 다시 누르면 풀린다(`aria-pressed`
반전, §3.7). 묶음 ID 가 없는 합성 항목(환불·미분류·이월 입금 …)은 좁힐 대상이 없어
버튼이 아니라 점선 윤곽의 읽기 전용 칩이다 — 틴트 면을 쓰면 바로 윗줄에서 '안 눌린
버튼'을 뜻하는 회색과 충돌한다. 합계 줄은 통장 카드가 이미 같은 수를 말하므로 뺐다.
회원 화면(`/my-dues/ledger`)에는 거래 목록이 없어 항목별 합계를 볼 자리가 이 시트뿐이라
거기서는 시트를 그대로 유지한다(`CashLedgerView`의 `buckets` 프롭).

입금의 부과 배분액을 해당 부과 항목에 먼저 넣고, 같은 달 연결 환불과 배분을 뺀 잔액을 세션 → 묶음 → 레거시 분류 → 미분류 순으로 귀속한다. 다른 달 원입금의 환불은 출금월의 환불 항목이다. 거래 내역에서 연결 취소가 가능하지만, 여러 용도가 섞인 입금은 현재 한 종류의 취소 경로를 우선 노출한다.

카테고리 추가/삭제 UI와 카테고리 기반 거래 필터가 아직 남아 있다. 새 거래의 묶음 선택과 이 관리 UI는 같은 항목 체계가 아니다.

### 3.4 회원 내 회비

Claude Design `콕타임 회계 v2` 3a 아트보드 구조다(2026-09-11). 읽기 전용이며 조작은 없다.
탭은 `내 회비`·`클럽 회계` 두 개이고 달 선택은 두 탭 위에 하나만 둔다 — 단 **달의 규칙이
탭마다 다르다**(내 회비는 이번 달까지, 클럽 회계는 지난달까지). 그래서 탭별로 달을 따로
기억한다.

**달의 정의는 부과 달이다.** `dues_groups.occurred_on`(회비=그 달, 대관비=회차 날짜,
수동=발생일)의 KST 달로 묶는다. 납부 달로 묶으면 `낸 돈 + 남은 금액 = 부과`가 깨져
한 카드가 서로를 부정한다(9월 회비를 10월에 내면 '낸 0 / 부과 29,000 / 남은 0'). 계산은
`src/lib/dues/myDues.ts`(`myDuesMonth`)이고, 서버 조회 `dues_read`가 본인 관련 부과·납기·
배분을 월 제한 없이 주므로 **달 이동에 재조회가 없다**(e2e 가 `dues_read` 호출 수를 단정).

- 첫 카드 = 그 달에 낸 돈(주인공) / 부과 총액 / 진행 미터 / 종류별 줄(회비·회차 대관비·
  수동 묶음) / 마지막 줄 `남은 금액`. 회차 줄의 보조 문구는 `N회차 중 M회차 납부`다.
  **마지막 줄은 합계가 아니다** — 위 줄들의 합은 히어로의 '낸 돈'이고 이 줄은 남은
  돈이다. 그래서 합계 기호(이중선·20px·틴트 면)를 쓰지 않는다(§3.7 '크기와 이중선은
  한 세트'). 반대로 납부 내역의 `합계`는 진짜 합이라 합계 기호를 쓰되, 줄이 하나면
  같은 수가 두 번 보이지 않게 합계 줄을 생략한다.
  서버 불변식(`dues_assert`)이 살아 있는 부과마다
  `부과액 = Σ 납기 잔액 + Σ 배분(해제 제외)` 을 강제하므로 세 숫자는 어긋날 수 없다.
  취소·면제 부과는 부과 총액에서 빼고, 전액 해제된 배분은 낸 돈으로 세지 않는다.
- **카드는 달 단위지만 알림은 아니다.** 계좌 위의 `?` 알림은 `memberSummary(…, 오늘)`의
  `toPay`를 말한다 — 다른 달 미납이 화면에서 사라지면 회원이 낼 돈을 못 본다. 미납은
  `unpaid/partial`만, 회비는 실효 월이 현재 월 이하인 것, 대관비·수동 부과는 월 무관
  전부다. 부분납은 남은 금액만 합산한다. 납기가 이월된 건은 그 달 카드의 `남은 금액`에는
  남지만 알림에서는 빠지고, 보조줄에 `납기 이월`로 표시한다.
- 대납(`payer_hint`) 금액은 본인 금액과 섞지 않고 별도 알림으로 안내한다.
- 초과 입금 잔액은 ‘회원 잔액’ 알림으로 안내하고 운영진에게 이월·환불을 요청하게 한다.
  앱에 계좌를 제출·저장하거나 환불을 송금하는 기능은 없다. 잔액 안내 대상은 **배분이
  일부라도 있고**, 묶음·분류·세션이 없는 본인 입금 중 `입금 − 전체 배분 − 전체 연결 환불
  > 0`인 거래다. `paid_by`가 있으면 그 회원, 없으면 배분 납부자로 본인을 찾는다. 배분이
  0인 오입금/전액 취소 잔액은 이 안내에 잡히지 않는다.
- 납기 전 금액은 `다음 정산`(앞으로 낼 돈 · 이미 낸 돈) 한 줄로 남긴다. 3a 에는 없는
  칸이지만 이월 예약이 여기서만 보이므로 유지한다(e2e 계약).
- `{n}월 납부 내역`은 통장 입금 1건이 한 줄이고 합계는 카드의 낸 돈과 같다. 이 달
  **부과**의 납부 내역이라 입금일은 다른 달일 수 있다(선납·후납) — 그래서 제목에
  '이번 달'을 쓰지 않고 달을 밝히고, 줄의 날짜는 실제 입금일을 그대로 보여 준다. 상태어는
  항상 `✓ 확인됨`이다 — 읽기 모델에 확인 플래그가 없고 **배분 행의 존재가 곧 확인**이다.
  아직 대조되지 않은 돈은 배분이 아니라 `positions`이고, 위의 회원 잔액 알림이 말한다.
  수동 부과 라벨과 신규 묶음 직접 입금 반영은 미완이다(§13 A09).
- 그 달에 실제로 나간 환불은 `환불` 시트로 따로 보여 준다.
- 공개 회계(클럽 회계 탭)는 별도 서버 RPC로 계산한다. 화면은 2026-07부터 지난달까지
  허용한다. 이 월 제한은 클라이언트 탐색 제한이며 RPC의 월별 마감 잠금은 아니다.
  **통장 잔액은 회원에게 없다** — 유일한 출처 `bank_transactions.balance_after`의 RLS가
  운영진 전용이라 3a 의 잔액 히어로는 서버를 바꾸지 않으면 채울 수 없다. 그래서 회원
  탭은 수입·지출·수입−지출까지만 말하고, 그 사실을 시트 아래 한 줄로 밝힌다.

### 3.5 앱 진입 알림

로그인·프로필 완료 회원에게 미납 또는 돌려받을 돈이 있으면 모달을 보여준다. 본인 화면과 미납 계산/환불 안내 컴포넌트를 공유한다. 보드에서는 표시하지 않고, `/my-dues` 진입은 읽은 것으로 처리한다. 닫기는 이번 실행에만 유효하며, 실행 중 재조회·실시간 납부 반영은 없다. 계정 전환 시 조회 스냅샷을 폐기한다.

### 3.6 수동 부과

종류·이름·발생일·선택적 참고 회차 → 명단 → 금액 → 저장 순이다. 참고 회차는 후보 명단의 재료이며 자동 부과 트리거가 아니다.

- 시작 명단: 식사 체크 / 참석(`confirmed/late_pool`) / 참석 ∪ 보드 / 최근 30일 참석 / 전체 회원 / 직접 선택 / 지난 명단.
- 필터: 비활성·게스트·운영진·명예회원 제외, 성별, 지난 명단 제외. 기본은 비활성·게스트 제외다.
- 최종 명단 = 필터 결과 ∪ 손으로 추가 − 손으로 제외. **‘실제로 뛴 사람’이라는 현재 라벨은 경기 출전 이력을 검사하지 않는다.**
- 금액: 총액 분할(10/100/1,000원 올림) 또는 인당 직접. 대관비의 정액 근처 스냅은 없다. 총액은 묶음에 저장하지만 올림 단위는 저장하지 않아 편집을 다시 열면 1,000원이 기본이다.
- 편집은 저장된 부과 명단에서 시작한다. 배분된 행은 금액/명단 변경에서 보호되어, 한 묶음에 여러 금액이 남을 수 있다(§4.4).
- 현황·부과 목록은 같은 수동 부과 카드/대조 시트를 쓴다. 대조의 미납은 살아 있는 부과의 잔액, 받은 돈은 무효·면제 포함 모든 행의 배분 합이다.
- 카드 마감은 `연결 지출 > 0 AND 미납 인원 = 0`이다. 묶음 직접 입출금은 선택 월만 조회하고, 직접 입금은 현재 **전액을 합산**한다. 모든 달의 부과 배분과 혼합되므로 묶음 전체 손익으로 신뢰할 수 없는 경우가 있다(§13 A05).

### 3.7 표기 규약(새 모드 화면 공통)

4탭(현황·정산함·회계·부과)과 회원 내 회비는 단일 행 프리미티브 `.ac-row`
(`거터 | 본문 | 금액 레일`)를 공유한다. 규약은 다음 다섯 개다.

- **금액**: `signedWon()`/`won()` 출력 + `.ac-amount`. 레일이 `tabular-nums`와
  `white-space: nowrap`을 강제하므로 개별 노드가 클래스를 빼먹어도 자릿수 정렬과
  줄바꿈 금지가 유지된다. 폭은 고정(`--ac-rail`)이라 늦게 도착하는 잔액이 열을
  밀지 못한다. 예외는 머리글에 `단위: 원`을 단 대조 시트다 — 회계(`CashLedgerView`)와
  회원 내 회비 카드·납부 내역은 단위를 머리글이 한 번 말하고 레일에는 숫자만 둔다.
  문장(알림·보조줄)에서는 언제나 `won()`을 쓴다.
- **방향**: 입금/출금은 색이 아니라 거터의 한 글자(`입`/`출`)로 말한다.
- **상태**: 색 하나로 말하지 않는다. 거터 글리프(`✓ ? ! —`) + 상태어(완납·미납·
  납기 이월·부과 제외…) + 색의 3중 인코딩이다. 회원 화면에는 거터가 없어(`--ac-gutter:0`)
  글리프를 상태어 앞에 붙인다(`✓ 확인됨`) — 세 채널은 그대로 유지된다.
- **선택**: `aria-pressed="true"`는 화면 전체에서 채움 반전 하나로만 표현한다.
  현재 탭(`aria-current`)은 지면 색으로 떠 있게 해 선택과 구분한다.
  운영진 화면(`/dues`)은 반전 채움이 파랑(`--ac-sel-bg`), 회원 화면(`/my-dues`)은
  먹색이다 — 아래 홈 톤 스킨 항목 참조.
- **라벨 축약**: `shortGroupLabel()`은 표시 전용이다. 접근명·검색·`select` 옵션의
  원문 라벨은 절대 바꾸지 않는다(e2e 계약).

깊이 규약: 이 화면군에 모달은 두 개만 남는다 — 회비 설정과 비가역 작업 확인
(`AccountingControls`의 `ConfirmDialog`). 부과 발행·취소 후 발행·이월·이월금
적용은 부과 탭의 인라인 전표(`ChargeVoucher`)에서 시작하고 끝난다. 정산함 카드는
접지 않는다(진입 즉시 조작 가능해야 한다는 계약이 e2e에 잠겨 있다).

레이아웃 규약: 고정높이 앱셸·내부 스크롤·`position: sticky`를 쓰지 않는다
(AppScreen의 body 자연 스크롤). `accounting.css`·`accounting-home.css`에
`dvh/lvh/vh/fixed/sticky/z-index/env()`가 없는 상태를 유지한다 — 확정 버튼은
무장된 슬롯 바로 아래 자연 흐름에 둔다.

홈 톤 스킨(`/dues` 전용): 운영진 4탭은 `accounting-home.css`가 위 규약을 유지한
채 색·표면·컨트롤·활자만 홈 화면 언어로 덮는다. 세 가지가 이 파일의 계약이다.

- **스코프**: 모든 선택자가 `.accounting-screen.ac-layout-v2`로 시작한다.
  **2026-09-11 부터 회원 화면 `/my-dues`도 이 클래스를 단다** — 운영진과 같은 홈
  톤이다. 따라서 "이 스킨은 회원 화면에 닿지 않는다"는 더 이상 참이 아니며, 스킨을
  고칠 때 회원 화면도 함께 확인한다. 세 파일을 `accounting.css` →

  공용 `CashLedgerView` 뿐이다(정산함·부과·거래 카드 계열이 없으므로 기하 동결
  구역과 겹치지 않는다).
  회원 전용 기하는 `accounting.css` §11(`.ac-mine-*`)에만 둔다. 행 기하를 페이지
  클래스가 아니라 카드·시트에 거는 이유는 같은 화면의 `.ac-cash-columns`(3열)를
  덮어써 지출 열을 죽이기 때문이다. 클럽 회계 탭도 운영진 래퍼 `.ac-ledger-page`를
  쓰지 않고 `.ac-mine-ledger`를 쓴다 — 그 래퍼에는 아래 거래 내역 표와 한 장으로
  잇는 스킨 규칙이 달려 있어, 표가 없는 회원 화면에 붙이면 시트 바닥이 열린다.
- **import 순서**: `accounting.css` → `accounting-layout.css` → `accounting-home.css`.
  동률 특정도가 다수라 순서가 곧 승패다. `@media print` 블록은 파일 맨 끝이어야

- **기하 동결**: `.ac-receipt-*`·`.ac-quick-*`·`.ac-settlement-*`·`.ac-transaction`·

그림자 0이고, 부양은 세 용도(탭 썸·선택 칩 / `.ac-armed`·주 확정 / 영수증 카드)

별칭을 라이트에서만 끊었다.


## 4. 부과 생성과 변경

### 4.1 자동 발행의 범위

현재 월 회비·대관비 **생성기**는 기존 부과의 금액·상태·대납자·당일취소 표식을 갱신하거나 삭제하지 않는다. void도 이미 존재하는 행으로 세어 추가 발행을 막는다. 이 원칙이 모든 수정 경로에 적용되는 것은 아니다(§4.4).

| 발생 계기 | 현재 동작 |
| --- | --- |
| 운영진이 당월 회비 관리에 진입 | `dues_ensure_monthly`: 그 달 회비 행이 하나라도 있으면 생성기 호출 자체를 생략 |
| 회차 상태가 closed로 전환 | 종료 트리거가 `p_initial=true`로 최초 발행; 기존 선납 외 나머지 대상을 계산 |
| 수동 월 재계산 | `generate_dues_charges`: 해당 월 회비와 회차 생성기 호출. 일반 화면 새로고침과 다름 |
| 입금 확인 | 선택한 항목을 즉석 발행하고 배분. 자동 자격/발행 대기와 별도의 운영진 경로 |
| 수동 부과 저장 | 운영진이 고른 명단에 즉시 발행/갱신. 발행 대기를 거치지 않음 |

새 대상이 없으면 생성기는 기존 초안을 정리하고 종료한다. 새 대상이 있을 때 대관비 인당 금액이 기본액의 절반 미만/2.5배 초과이면 `amount_out_of_range`, 회비 대상 수가 전월 발행 수의 ±40% 밖이면 `head_count_jump`(전월 10건 이상일 때), 기존 발행 묶음에 추가 대상이면 `new_members`로 대기한다. 대관 최초 종료 발행은 선납 때문에 `new_members`로 보류하지 않는다.

[발행]은 **저장된 초안**을 부과에 삽입하고 초안을 지운다. 발행 직전 최신 자격/금액을 다시 계산하지 않는다. [폐기]는 초안만 삭제하므로 이후 생성기 재실행 시 다시 후보가 될 수 있다. 영구 면제/부과 취소와 다르다.

### 4.2 월 회비 대상

대상 함수는 `dues_monthly_targets(ym)`이다.

1. 현재 활성, 비게스트, 비명예회원, 비운영진이어야 한다.
2. `(membership_started_at 또는 created_at의 KST 날짜) + offset_days`가 속한 달의 **다음 달부터** 부과한다.
3. 실제 합류일은 `max(created_at, rejoined_at)`의 KST 날짜다. 합류일이 설정 컷오프(기본 21일) 이상이면 **그 합류월**은 제외한다. 합류 이전 모든 달을 막는 규칙은 아니다.

재활성화는 `rejoined_at`을 기록한다. 가입일 보정·재활성화·명예 해제 후 이미 일부 발행된 달은 월진입 ensure가 나머지를 만들지 않는다. 수동 재계산 시에는 추가 대상이 발행 대기로 갈 수 있다. 특정 달 자격을 완전히 복원하는 회원 상태 이력/금액 정책 이력은 없다.

### 4.3 대관비 대상

자동 생성 자격은 **대관 장소 + active/closed + 시작 시각 있음 + 경기 기록 있음**이다. 통상 종료 이벤트에서 생성하지만 수동 재계산은 active도 계산한다. `dues_include` 컬럼은 현재 생성기·세션 목록 조회의 예외 조건으로 쓰이지 않는다.

대상 = `(confirmed/late_pool + 부과 대상 당일취소) ∪ member_id가 있는 보드 명단`, 이후 정액일 때만 운영진을 제외한다. 비활성·명예 여부는 대관비 면제 조건이 아니다. 보드에서 뺐어도 참석 명단으로 대상이면 남고, 대기/사전취소여도 보드에 있으면 포함한다. 회원 ID 없는 셋업 게스트는 제외한다.

당일취소는 `cancelled` + 확정 시각 있음 + 취소일과 회차일이 KST로 같음 + **확정에서 취소까지 1시간 이상**이다. 정확히 1시간이면 부과 대상이다. 재신청하면 마지막 확정 시각부터 다시 잰다. 두 유료 모드 모두 적용하며, 보드에도 있으면 참여자로 취급해 당일취소 표식을 붙이지 않는다.

게스트 부과는 해당 회차 초대자를 `payer_hint`로 둔다. 정원 초과 확정(우선참여권 포함)은 분모와 부과에 포함한다. 운영진/신규 프리패스의 장소 게이트와 회차 총액 0원의 무부과는 별개의 조건이다([참석 규칙](EXPANSION_SPEC.md) §5.1).

### 4.4 이미 발행한 뒤의 조작

| 조작 | 부과에 미치는 영향 | 기존 납부/잔액에 미치는 영향 |
| --- | --- | --- |
| 자동 생성기 재실행 | 기존 행 불변, 없는 사람만 발행/대기 | 기존 배분 불변 |
| 회원 비활성화(본인 탈퇴 포함) | **월 무관**, unpaid·배분 0·이월 없음인 월 회비 삭제 | 부분/완납·대관비·수동 부과·이월·void/waived 보존 |
| 명예회원 지정 | **월 무관**, unpaid·배분 0인 월 회비 삭제; 이월도 삭제 대상 | 부분/완납·다른 종류·void/waived 보존 |
| 부과 void/waived | 행과 금액 보존, 미납 의무만 제외 | 배분을 풀거나 환불하지 않음 |
| 부과 reset | 배분 합계로 unpaid/partial/paid/overpaid 복원 | 배분 불변 |
| 입금 처리 취소 | 부과는 남고 배분 합계/상태 재계산 | **그 입금의 전체 배분** 삭제. 통장 원본·연결 환불·묶음은 남음 |
| 회차 총액 저장·재발행 | **완납·부분납·void·waived 포함 해당 회차 부과 전부 삭제 후 새 ID로 재생성** | 먼저 해당 회차의 배분 전부 해제. 다른 부과에 사용한 배분은 보존. 은행 거래는 남아 재처리 필요 |
| 수동 부과 명단/금액 저장 | 배분 0인 기존 행만 갱신, 빠진 사람 중 배분 0·void 아님 삭제 | 배분된 사람은 금액·이름·날짜까지 기존 값 유지. 제외했어도 남음 |
| 수동 부과 묶음 삭제 | 배분 0인 부과는 void 포함 삭제 | 배분된 행은 남음; 환불이 아님 |

총액 재발행은 원본 부과/납부 요약을 감사 로그에 남기지만, 과거 취소 결정을 새 부과로 계승하지 않는다. 새 부과가 회원 화면에 즉시 미납으로 보일 수 있다. **‘미납분만 금액 정정’은 폐기된 설명**이다.

수동 부과는 기존 0원 배분 void/waived 행의 금액·라벨도 수정할 수 있으나 상태를 reset하지는 않는다. 대관 전체 재발행과 수동 부과 수정은 현재 서로 다른 정책이다.

## 5. 납부자와 금액 제안

이름은 적요에서 날짜·회비 등의 문자열을 제거한 뒤 정확/부분 일치로 제안한다. 검색은 초성도 지원한다. 확정은 운영진의 버튼 조작으로만 발생하지만, **첫 후보가 납부자로 미리 선택**된다.

- 비게스트 동명이인은 모두 유지한다. 동명 게스트는 일부 접되, 미납/예정 참석 ID는 보호한다. 자동 제안 최대 5명, 칩 최대 4명, 검색 결과 최대 6명이다.
- 일반 회원은 성별·출생연도를 보조 표시하고 게스트는 ‘게스트’로 표시한다. 동명 게스트를 전부 구분할 방문/초대자 정보는 없다.
- 납부자가 이미 선택된 상태에서 검색 결과를 고르면 **납부자 교체가 아니라 ‘함께 낼 사람’ 추가**다. 신규 회비 칩은 납부자 본인에게만 생긴다.
- 금액 자동 선택은 납부자 입금월 회비 + 기존 대관/수동 미납 + 예정 회차 선납에서 실제 금액 합이 입금액에 정확히 맞는 조합을 찾는다. 없으면 선택하지 않는다. 신규 수동 묶음 추가·이미 열린 회차의 신규 부과는 수동 선택이다.
- 서버는 선택 항목 순서대로 남은 입금 한도까지 배분하므로 부분납이 가능하다. 미납 부과의 회원 ID와 배분의 납부자 ID는 대납을 위해 다를 수 있다.

동명이인 실제 장애의 원인은 운영 데이터로 확인되지 않았다. 이름으로 저장이 합쳐진다고 단정하거나 이름만으로 회원을 병합하지 않는다(기획안 T04).

## 6. 환불·이월·다른 달 처리

### 6.1 현재 환불이 하는 일

`dues_link_refund(out, in)`은 날짜 제한 없이 출금과 입금을 연결한다. 순차 처리에서 검사하는 한도는 `기배분 + 기존 환불 + 이번 출금 <= 원입금`이다. 출금 한 건은 원입금 한 건만 가리키며, 한 입금에 여러 환불 출금은 가능하다.

**이미 부과에 사용한 금액은 그대로 환불할 수 없다.** 그 배분을 해제하고 부과 의무도 별도로 조정해야 한다. 납부 연결만 취소하면 원부과가 다시 미납이 된다. 지금은 개인별 감액 → 잔액 발생 → 환불을 묶어 처리하는 흐름이 없다.

DB는 다른 달 연결을 허용하지만, 정산함 후보·연결 환불 합계·거래 내역 점프는 현재 월 거래만 이용한다. 따라서 ‘8월 입금 → 9월 환불’은 **DB 지원 / 화면 경로 미완**이다.

### 6.2 세 종류의 ‘다음 달’

| 상황 | 현재 가능한 범위 |
| --- | --- |
| 아직 안 낸 8월 회비를 9월에 내기 | 회비 이월. 원부과 다음 달로 1회, unpaid/partial만 허용 |
| 8월 잔액을 이미 발행된 9월 부과에 사용 | 원입금 재처리와 월 무관 기존 미납 배분으로 가능. 부분 처리 UI 등의 제약 있음 |
| 8월 잔액을 보관했다가 아직 없는 미래 부과에 사용 | 회원별 보관 잔액·사용 예약·환불 대신 보관 선택 기능 없음 |

이월 해제는 배분이 있으면 거부된다. 이월분 [정산]은 면제이므로 현금/통장 납부의 증빙으로 사용할 수 없다. 잔액을 묶음에 붙이는 것은 클럽 수입 귀속이며, 해당 회원의 미래 납부금 보관과 다르다.

## 7. 통장 가져오기

운영진 [가져오기] → `ingest-bank-email` Edge Function → Apps Script가 Gmail 원문 반환 → 토스 파서 → 원문 보관·거래 적재 순이다. `dedup_key`로 중복 적재를 방지한다. 수입/지출은 실제 은행 거래로 기록하며 현금 납부·앱 내 송금은 없다. 가져오기는 부과 생성이나 자동 납부 확정이 아니다. 다은행 어댑터/LLM 파싱 폴백은 미구현이다.

## 8. 금액과 상태의 계산 범위

부과의 `amount_paid`는 연결된 배분 합계다. 일반 상태는 배분 0=unpaid, 부과액 미만=partial, 같음=paid, 초과=overpaid이고, void/waived는 배분 합계가 변해도 유지한다. 신규 배분은 void/waived에 금지된다. 거래의 matched는 ‘전액 납부’와 같지 않으며, 전액 환불·직접 귀속도 처리 완료다.

월 통장 회계의 기준은 **항목 순액 합 = 실제 입금 합 − 실제 출금 합**이다. 운영진은 클라이언트, 회원은 서버에서 별도로 분해한다. 일반 배분/묶음 경로는 같은 취지지만, 세션에 배분과 직접 귀속을 겹치거나 묶음/세션에 환불을 겹치면 서로 다른 산식을 사용한다(§13 A08). 이 불변식이 모든 허용 조합에 구현되어 있다고 단정하지 않는다.

회차 대조는 전체 기간의 부과 배분·세션 직접 거래를 읽는다. 수동 묶음 카드는 전체 기간 부과 배분과 현재 월 직접 거래를 섞는다. 두 화면을 모두 ‘발생 기준 전체 손익’이라고 부를 수 없다.

## 9. 알림

입금 배분 확인 시 선택한 납부자가 비게스트이면 `payment_confirmed` 알림을 만든다. 이미 발송된 알림은 납부 연결 취소로 회수되지 않는다. 운영진의 선택 미납 발송 UI/래퍼는 제거됐고, `dues_notify_selected` RPC만 잔존한다. 회원의 미납/환불 잔액 안내는 §3.5의 앱 진입 모달이 담당한다.

## 10. 권한

운영진의 주요 발행·배분·환불 조작은 `is_admin()`을 검사하는 RPC다. 설정 변경 등은 RLS를 적용한 직접 UPDATE도 사용한다. 따라서 ‘모든 쓰기가 RPC’라는 설명은 맞지 않는다.

회원 부과 조회는 본인 또는 `payer_hint`를 명시 필터하며, 운영진 계정의 내 회비에도 같은 필터를 사용한다. 은행 원장과 초안은 운영진용이다. 본인 납부/잔액 RPC는 회원 ID로 제한하고, 공개 장부와 클럽 계좌는 로그인 열람 경로다. 공개 장부의 UI 월 제한과 서버 권한 검사는 별개다. 회원의 하드삭제는 회계 연결 유실 때문에 금지하고 탈퇴는 비활성화한다.

기타 잔존/미구현: `dues_include` 예외는 현재 조회·생성에 미연결, 금액 정책 이력(`dues_policies`)·다은행 파서는 없음. 자동 확정/학습 별칭/현금 납부는 과거에 폐기한 기능이며 이번 TODO의 재도입 대상이 아니다.

검증: 관련 기존 단위 테스트 7개 파일 **165개 통과**(2026-09-07). 대상/금액 계산·이름 후보·미납 판정의 확인이며, 위 화면 통합·DB 동시성·운영 데이터 문제까지 해결됐다는 뜻은 아니다.


## 14. 새 부과 구현과 기존 운영의 경계

`20260907030000_dues_v2.sql`과 `src/components/accounting/`에 새 원장과 화면을 구현했다. **운영 DB에 새 스키마를 설치했으며 기존 금융 자료는 동일하다. 새 모드는 2026-09-07 12:00 KST 에 활성화했다(`enabled=true`·`paused=false`, [적용·복구](ACCOUNTING_ROLLOUT.md) 참조).** 새 스키마 설치만으로 기존 부과가 바뀌지 않으며 `dues_v2_control.enabled`가 참일 때 새 화면·쓰기 경로를 사용한다. 모드 조회 실패 시 기존 쓰기로 임의 전환하지 않는다.

### 14.9 TODO 선택 흐름 보완 (2026-09-07)

환불은 납부자를 이름·초성으로 찾아 명시적으로 선택한 뒤 전체 기간의 본인 원입금을 확인한다. 은행 적요의 이름과 실제 납부자 ID는 별개다. 동명이인과 대납자의 돈은 소유자 ID로 나누고, 미매칭 입금은 소유자 확인과 환불을 같은 작업으로 기록한다. 남은 돈도 그 회원 잔액으로 보존한다. 기존 사용액·누적 환불·클럽 귀속을 뺀 환불 가능액을 표시하며 부족한 입금도 이유와 함께 조회할 수 있다.

같은 KST 날짜·장소의 회차만 시간을 추가하고 같은 시간대는 회차명/번호로 구분한다. 수동 부과 참고 명단을 선택할 때에도 동일하게 표시하고 회차 ID를 발행 근거에 보존한다. 운영 적용 상태와 검증은 `ACCOUNTING_ROLLOUT.md` §8을 따른다.

### 14.10 합산 입금 대납과 기존 납부 안내 (2026-09-13)

정산 카드의 **다른 회원 대납**에서 회원·게스트를 검색해 그 사람의 기존 미납을 추가한다. 본인 몫과 여러 회원의 미납을 같은 입금 잔액 안에서 선택하고 한 번에 확인할 수 있으며, 일부 정산을 마친 입금의 남은 잔액에도 같은 경로를 제공한다. 대납 대상과 금액은 항목 및 확인 요약에 표시한다. 저장은 기존 `pay` 명령의 `proxy=true`를 사용해 원입금 소유자와 기존 배분을 유지한다. 대납 취소는 해당 회원의 미저장 선택만 제거한다. 다른 회원의 아직 발행되지 않은 예정 대관은 이 미납 대납 목록에 포함하지 않는다.

입금 적요에 적힌 날짜(MMDD)의 대관비가 다른 원입금으로 완납되어 있으면, 해당 부과와 이전 입금 날짜·적요·금액을 카드에 표시한다. 이번 입금은 별도 잔액임을 안내하며 부과를 중복 생성하거나 자동으로 다른 회차에 연결하지 않는다. 부분납·납부 해제·면제·취소는 완납으로 표시하지 않는다.

납부 처리 내역은 실제 부과 대상 회원을 표시하고, 입금 소유자가 다르면 별도로 대납자를 표시한다. 연결 해제 버튼의 접근성 이름과 확인 요약에는 부과 대상·회차·해제 금액을 포함한다. 해제 금액이 돌아갈 입금 소유자도 확인 요약과 처리 사유에 기록한다. 한 입금으로 같은 회차의 여러 사람을 납부한 경우에도 대상별로 구분해 해제하며, 해당 부과만 미납으로 돌아간다.
